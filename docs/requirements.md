# itxiaAgent 知识库系统需求文档

## 1. 项目定位与目标

### 1.1 系统要做什么

建设一个供 itxiaAgent 使用、由社团持续维护的电脑知识库系统，将语雀笔记、维修经验和购机评测等资料整理为**可检索、可引用、可更新、能说明适用条件的知识**。

它需要支撑师生咨询和社团成员工作，辅助Agent回答电脑常识，结合需求给出购机参考，辅助维修排查，并沉淀成员经验。

本文保留完整业务目标及后续能力；首期交付知识查询／维护 API 和管理命令，Django Admin 网页界面按需启用。下述面向用户的回答、追问与转人工效果由外部 Agent 配合实现，阶段划分见第 3 节。数据对象、接口字段和阶段状态以[首期技术设计](/home/kurfuerst/Coding/nju/itxiaRAG/docs/phase1/phase1-technical-design.md)为唯一细节契约，通用测试规则见[项目单元测试规范](/home/kurfuerst/Coding/nju/itxiaRAG/docs/unit-testing-guidelines.md)。

### 1.2 要解决的问题

以下是根据业务场景识别的需求动因。

| 问题 | 对业务的影响 | 系统应提供的改善 |
| --- | --- | --- |
| 知识散落在笔记、维修记录和推文中 | 查资料需要切换来源，已有经验难以复用 | 统一接入、整理和检索，并保留原始出处 |
| 师生反复提出基础问题 | 社员需要重复解释同类知识 | 提供易懂、有依据的常见问题回答 |
| 购机建议依赖预算、用途和时间 | 旧推荐、不同配置和不同价格容易被混用 | 按需求筛选候选，明确具体配置、推荐依据和资料日期 |
| 维修描述不完整，相同症状可能有不同原因 | 容易过早判断故障，或者照搬不适用的处理方法 | 补齐必要信息，提供有条件的排查流程和相似案例 |

### 1.3 成功的业务表现

- 师生获得与问题相关、能够理解的回答，并能找到关键依据。
- 购机咨询能够解释“为什么适合、有什么取舍、信息截至何时”。
- 维修辅助能够给出下一步可执行的检查，以及需要停止操作、联系社员的条件。
- 社员能够快速找到相似案例和经过整理的流程，不必从多份资料中重新拼接。
- 维护者能够发现缺失或过期知识，完成更新后让后续回答采用新内容。


## 2. 用户与典型场景

### 2.1 用户角色

| 角色 | 主要需求 | 默认知识可见范围（建议） |
| --- | --- | --- |
| 普通师生、新生 | 电脑常识、购机建议、基础故障自查 | 已通过质量放行的公开知识 |
| 社员 | 查找案例、专业参考、排查流程、提交经验 | 公开知识及获授权的社团内部知识 |
| 知识维护者 | 确认来源范围、整理资料、异常复核与抽查、纠错更新、检查知识覆盖 | 管理权限范围内的来源与知识；原始敏感记录另行限制 |


### 2.2 核心使用场景

| 编号 | 场景与输入示例 | 需要完成的任务 | 预期结果 |
| --- | --- | --- | --- |
| S-01 | 常识咨询：“内存和硬盘有什么区别？” | 找到准确解释，按照用户基础组织内容 | 易懂的解释、实际使用影响、必要的参考出处 |
| S-02 | 新生购机：“预算 6000 元，学计算机，尽量便携，买什么？” | 澄清关键用途和约束，查找适用的近期推荐与评测 | 候选机型或配置方向、具体版本、取舍、资料日期；缺少当前资料时说明限制 |
| S-03 | 客户：“电脑很卡，风扇一直响。” | 收集系统、现象和近期变化，优先提出低风险检查 | 可能原因、按顺序进行的检查、结果分支、停止条件 |
| S-04 | 社员维修：“某型号不能开机，有没有处理过？” | 匹配症状、设备和已做检查，检索相似维修记录 | 案例过程、处理结果、适用差异和相关流程，不把相似案例视为已确诊 |
| S-06 | 新成员学习或准备科普讲座 | 围绕主题汇总知识、常见误区和案例 | 有出处的学习提纲或讲座素材清单；完整课件制作可后续扩展 |
| S-07 | 维修结束后补充经验 | 将记录脱敏、补齐关键信息、关联已有知识并审核 | 新案例入库；有复用价值的内容进入 FAQ 或操作流程草稿 |
| S-08 | 旧购机文章失效，或维修方法被纠正 | 更新来源、标记旧结论、处理依赖该来源的整理内容 | 默认检索使用当前已放行内容；替换后旧引用失效，后续派生内容重新审核 |

## 3. 系统边界与首期范围

### 3.1 知识库与外部调用方的职责

| 责任方 | 主要职责 |
| --- | --- |
| 知识库系统 | 接入与整理资料，保存来源与当前构建，管理知识可见性、有效性与关联，提供检索证据、引用查看、维护和反馈接口，支持检索评估；保留原始查询的意图识别／改写扩展点 |
| 外部 Agent／客户端 | 可整理查询与已确认条件，也可提交原始查询；维护对话并根据返回信息追问、组织最终回答或转交志愿者；Agent 开发不属于知识库首期实现 |
| 社团成员 | 确认知识是否准确、批准发布、完成实际维修、处理复杂问题与经验修订 |

### 3.2 优先级约定

- **P0：首期必需。** 分阶段支撑导入、维护、检索，并在最终迭代补齐反馈闭环；全程保证证据可追溯、权限正确和必要的维修风险信息完整。
- **P1：后续增强。** 在首期可用后改善知识覆盖、维护效率和复杂问题效果。
- **P2：探索项。** 只有在具体场景与评估收益明确后再投入。

### 3.3 建议的首期范围

1. 支持人工导入三类现有来源的授权文本，以及必要的来源元数据。首期无需自动连接所有平台。
2. 形成小规模、经过整理的来源片段、产品配置、购机条件、维修案例和排查步骤记录；使用可引用的父上下文承载完整内容、子块负责检索；不建设独立的 FAQ／主题页／Spec 编辑模块。
3. 为外部 Agent 或其他客户端提供带引用的知识库检索结果，支持公开／内部权限、机型配置、时间和知识状态过滤。
4. 覆盖常识、基本购机和低风险故障场景所需的证据查询，以及志愿者案例检索；最终回答、追问和转人工由调用方负责。
5. 提供自动质量放行、异常人工复核、更新失效和离线检索评估能力；问题反馈在最终迭代启用，早期版本只返回查询标识和结构化 Trace。

首期暂不实现 M6 知识页、Spec 和派生证据整理。来源片段、结构化字段、来源与构建、原文位置、权限和证据接口仍是首期必需能力，否则无法满足来源追溯和权限要求。Agent 开发、追问逻辑和最终回答生成由外部应用单独建设。知识库首期只实现查询预处理接口和默认透传，意图识别、查询改写及其模型接入列为可选 P1 增强。

父子分块的第一个具体实现先用笔吧笔记本评测验证：同一文章一台笔记本一个父段，多台则多个父段。该规则属于评测处理器，其他文档按各自 Schema 的完整语义边界生成父段；三类来源及常识、购机、维修的首期目标保留。检索返回完整父上下文及命中子块引用，具体数据与返回契约见首期技术设计。

与[首期需求与技术选型](/home/kurfuerst/Coding/nju/itxiaRAG/docs/phase1/phase1-requirements-and-selection.md)的模块边界对应如下：

| 模块 | 本次确认的职责与阶段 |
| --- | --- |
| M1：Web、维护入口与 API | Django 提供认证、ORM、迁移和管理命令，DRF 提供知识查询与维护 API；Django Admin 为可选维护界面，不作为首期前置 |
| M4：管线与任务执行 | Python 模块化导入流程 + PostgreSQL 任务表 + 单 Worker；Haystack 作为后续可选编排框架 |
| M5：查询预处理与检索 | 首期预留可替换处理器、透传与跳过路径；后续接入规则／LLM，不改变召回和证据接口 |
| M6：知识页、Spec 与派生证据整理 | P1，首期暂不实现；F-17 保留为后续需求，不影响首期来源片段的证据追溯 |
| M7：知识库对外接口 | 定义查询、证据返回、引用查看、反馈和维护接口；不开发 Agent 或直接适配模型，与 M1 共用 DRF 服务；可选查询理解模型封装在 M5 |


## 4. 数据来源与知识范围

### 4.1 已知来源及接入要求

| 来源 | 预期内容价值 | 首期接入建议 | 必须保留或确认的信息 |
| --- | --- | --- | --- |
| 社团语雀笔记 | 基础知识、历史教程、社团流程与接受 | 由成员授权导出或提供文本，保留标题层级和必要表格 | 文档标题、原始地址或文档标识、作者／维护者（如有）、更新时间、内部或公开属性 |
| 维修经验记录（文本） | 真实症状、排查过程、处理方法与结果 | 批量导入脱敏文本，再整理为案例 | 记录时间、设备与系统、症状、已做检查、处理和结果；缺失内容保留为未知 |
| 笔吧评测室公众号推文等 | 机型评测、阶段性购机建议、配置和参考价格 | 在权限允许范围内人工整理或导入正文与摘要 | 原文标题、作者／账号、原始地址、发布日期、机型配置、价格时间及条件 |
| 后续可补充的官方资料 | 厂商规格、操作系统说明、设备支持文档 | 根据知识缺口补充 | 官方出处、适用型号或软件版本、更新时间；尚不视为已经拥有的数据 |

补充要求：

- 接入方式须在抽样后确认，不能预设语雀 API 权限、公众号批量获取能力或源文件导出格式已经具备。
- 对于只有图片才包含关键配置的文章，首期可人工补录；未解析的图片、表格必须标记，不能把残缺正文当成完整资料。
- 原始内容仅在授权范围内保存；不能保存全文时，保留允许使用的摘录、结构化事实、元数据和原文链接。
- 来源发布／更新时间与系统导入时间分开记录；无法取得原始日期时标为未知，不能用导入时间冒充。

### 4.2 应管理的知识类型

| 知识类型 | 内容示例 | 必要约束 |
| --- | --- | --- |
| 概念与 FAQ | CPU、内存、硬盘、备份、系统更新 | 解释准确，注明依赖的软件版本或适用范围 |
| 产品与配置 | 型号、年份、CPU、GPU、内存、存储、重量、扩展性 | 系列名不能代替具体配置；不混用不同年份或版本的数据 |
| 评测与推荐结论 | 性能、噪声、续航、适合人群、优缺点 | 区分客观参数、测试条件和作者主观评价 |
| 价格与购机条件 | 某日期、某配置在某渠道的参考价 | 关联时间、配置、渠道及补贴／优惠条件（如来源提供）；不当成当前成交承诺 |
| 维修案例 | 症状、检查、原因判断、措施、结果 | 区分已观察事实、推测和已确认结论；单个案例不代表普遍规律 |
| 操作与排查流程 | 清理启动项、检查磁盘占用、排查无法联网 | 有前提、步骤、结果判断、风险提示和停止／转人工条件 |
| 主题知识页（P1） | 购机入门、常见蓝屏问题、电脑维护 | 汇总内容保留原始证据，标明整理与审核状态；首期暂不实现 |

首期的概念问答和操作流程以来源片段及必要字段保存，可导入已有 FAQ 或流程文档；独立 FAQ／主题页／Spec 的编辑、派生内容与依赖管理归 M6，列 P1。

### 4.3 通用元数据与适用条件

首期只提供当前已放行内容，不要求历史正文查询或回滚；更新与重建统一通过新的导入任务，自动校验／必要人工复核后发布。这里的构建标识用于区分本次导入和引用，不承诺来源历史版本；Schema、处理器和模型配置仍可单独记录版本。每份来源及每条可引用知识至少能够关联：稳定标识、标题、来源类型、来源定位、构建标识、原始日期（可未知）、导入时间、访问范围、发布状态及审核信息。对由来源整理出的内容，还应记录其依赖的来源与构建。

按内容类型补充机型、年份、配置、系统／软件版本、症状、用途、预算、风险等级、适用条件等字段。只要求当前任务需要的字段；未提供或无法判断的值记为未知，不让模型补造参数、价格、故障原因或维修结果。

### 4.4 可信度、冲突与时效规则

- **按结论类型判断依据。** 产品规格宜以对应型号的官方资料核对；评测体验须保留测试条件；维修案例只证明该次记录中的现象与结果，不设一个适用于所有知识的来源总排名。
- **明确证据状态。** 区分来源明确陈述、社团审核整理、个案经验和待验证推测。首期不要求用一个看似精确的分数表示全部可信度。
- **保留冲突。** 同一配置的参数或同一问题的处理方法存在冲突时，展示来源和适用条件，提交维护者处理；不能仅因一条资料更晚就认定其必然正确。
- **按类型管理时效。** 价格和阶段性推荐需要更频繁复核；系统操作说明按版本复核；基础概念可较低频复核。具体周期由首批资料与维护能力确定。
- **不制造“最新”。** 对当前购机问题，过期或日期未知的资料只能作为带说明的历史参考；如果没有近期证据，提供选购原则并说明仍需核实的价格或机型信息。

## 5. 功能需求

### 5.1 数据接入、整理与维护

| 编号 | 优先级 | 需求 | 可观察的验收条件 |
| --- | --- | --- | --- |
| F-01 | P0 | 人工导入授权的文本／Markdown 及来源信息，支持上述三类来源 | 每类来源至少有一份样本成功入库；保留有效标题、正文和来源信息，并报告导入成功或失败 |
| F-02 | P0 | 整理文档结构，去除无关噪声；检索单元保留必要的上下文 | 不能把操作步骤与其警告、适用条件拆成无关联内容；摘录可定位回对应原文段落或可核查位置 |
| F-03 | P0 | 识别重复导入及已有来源的内容更新 | 等价的当前构建／有效候选不重复创建；新构建自动／人工放行并发布后生效，失败保留当前内容；旧引用返回不可用 |
| F-04 | P0 | 从资料整理产品、概念、案例、流程等知识；统一常用别名和术语 | 常见俗称可找到对应知识；相似名称的不同年份、配置和设备类型仍然保持区分；不确定关联进入待确认状态 |
| F-05 | P0 | 自动质量放行、异常复核、停用、修订和来源撤回 | 正常任务按已验证规则自动发布，未放行候选不能查询；停用内容不再检索或引用；维护者可查看自动／人工操作记录 |
| F-06 | P1 | 对具备权限和稳定接口的来源增量同步，并提醒复核 | 同步失败可见且可重试，不覆盖仍有效的当前构建；未配置自动同步的来源可继续人工更新 |

F-05 的首期流程为“提交候选 → 构建与自动校验 → 正常自动放行／异常人工复核 → 统一发布服务切换当前构建”。来源授权和可见范围事先确认，新文档类型、解析器或分块规则先人工验证代表性样本，再对同配置正常资料自动发布；不要求逐篇、逐子块人工审核。硬错误不得强制发布，日常按来源／处理器抽查内容与父子归属。任务进度、放行结论与来源状态分开记录，复用现有字段和质量报告，不新增审批表。修订正文或内容字段须提交新任务；候选待复核期间旧构建继续服务，已发布内容可标记过期／待复查，已知错误或高风险失效立即停用。

撤回、删除或更改访问权限时，首期先在权威层阻断访问，再处理片段、检索索引和已有缓存，引用查看也须检查当前状态。后续建设 M6 时，再将依赖来源的主题页和 Spec 纳入失效／复核处理，避免原文已撤回但旧摘要仍可被使用。

### 5.2 检索与知识库对外接口

| 编号 | 优先级 | 需求 | 可观察的验收条件 |
| --- | --- | --- | --- |
| F-07 | P0 | 支持原始／已整理查询、关键词、精确型号和错误信息检索，预留查询预处理模块 | `query` 接受原始问题和改写文本；透传／跳过路径均可查询，处理器可替换且失败可回退；首期不要求意图识别或 LLM 改写 |
| F-08 | P0 | 根据权限、知识状态及问题所需的设备、版本、时间等条件筛选证据 | 普通用户检索不到内部知识；型号或版本不匹配的材料不被当成直接依据；缺少过滤条件时可提示补充 |
| F-09 | P0 | 向外部调用方返回证据及其解释所需信息 | 结果包含摘录、来源定位、构建标识、日期、适用条件、知识类型和必要警告；可表达无结果、证据不足、冲突或资料过旧 |
| F-10 | P0 | 保留检索结果的来源追溯信息，支持授权范围内的出处查看 | 证据 ID 可定位到来源、构建和原文位置；引用查看再次检查权限及撤回状态，不实现回答断言与证据的自动核验 |
| F-11 | P1 | 支持关联查询，例如从症状查原因和检查步骤，从需求查配置与产品 | 能解释关联路径及各环节依据；无法证明的推断保留不确定性，不将关系链直接当作确诊 |
| F-26 | P1 | 按问题场景配置静态检索偏好 | 维修可优先案例与流程，购机可优先规格与推荐；在固定问题集比较相关性和漏召回，偏好不能越过权限、显式过滤或设备适用性约束 |

首期查询接口接收原始或已整理文本 `query`、可选场景 `scenario` 和已确认条件 `confirmed_context`，不要求完整对话。M5 通过统一的查询预处理接口衔接分词、向量化、条件检查与证据召回；首期默认透传，`preprocess=bypass` 可主动跳过，API 客户端即可独立使用。

接口应能让调用方明确区分条件未知与请求错误：预算对象、用途／症状／检查数组、知识类型和来源筛选使用技术设计第 6.2.1 节的固定 Schema。未知数组省略，`checks_done=[]` 表示尚未检查，数组传 null 属于格式错误；合法但条件不足时返回 `missing_conditions` 的稳定字段路径。实现以 DRF Serializer／生成的 OpenAPI 对接，不让各客户端自行猜测类型、枚举和默认值。

意图识别、关键词提取、查询改写和候选条件提取保留为 P1 扩展，可按需在知识库中接入规则或 LLM，外部 Agent 也可继续自行处理。处理器不得覆盖调用方显式场景、已确认条件或权限；提取结果作为待确认建议，失败回退原始输入。首期验收模块可替换和透传行为，后续启用智能处理时另行比较检索收益、事实保真、延迟与成本，不把生成模型作为首期运行前提。

知识库返回的证据、引用标题、摘录和来源地址均需符合访问范围。若内部资料要服务公开咨询，应先由维护者确认脱敏与公开授权，再按统一质量规则发布独立公开来源，不能只隐藏原文链接而继续输出内部内容。对外接口还提供获授权维护者的来源提交、状态查询、修订和审核等动作，与管理命令和可选 Admin 共用业务规则。

#### 5.2.1 按场景选择检索策略的阶段安排

- **首期 P0：** 保留 `scenario`、知识类型过滤和来源元数据，最终首期默认采用词法与向量混合检索。调用方可显式限定知识类型或具体来源；仅传入 `scenario=repair` 不自动变成“只查语雀／维修记录”，场景主要用于条件检查和适用性判断。
- **后续 P1（F-26）：** 增加可配置的静态场景策略。维修优先相关维修案例和操作流程，语雀中的维修教程、社团经验记录可作为优先候选；购机优先产品规格、评测与推荐，常识优先概念和 FAQ。偏好依据内容类型、问题相关性与适用条件，不能把整个平台当成对所有问题都更可信的来源。

场景默认偏好采用软排序或候选配额，仍保留其他相关证据的召回机会；调用方显式指定的类型／来源范围才是硬过滤。优先候选不足时，在原权限与显式过滤范围内补充其他相关资料，不能扩大访问范围或把不相关内容补成答案。场景不明时使用通用策略，不要求为此提前实现 LLM 意图识别。

P1 验收覆盖维修、购机、常识及跨类型问题：与首期基线比较有效证据命中、关键证据完整性、延迟及退化案例；确认相关的非优先来源仍可返回，不相关的优先来源不会仅因标签排在前面，权限和显式过滤始终生效。策略配置可追溯、可回退；此项不作为首期交付或首期技术方案的新增实现要求。

### 5.3 场景证据与外部回答约束

下表 P0 验收知识库返回的证据、条件和状态，可通过 API 测试客户端完成。问答、追问和转人工的交互行为由外部 Agent 实现。

| 编号 | 优先级 | 需求 | 可观察的验收条件 |
| --- | --- | --- | --- |
| F-12 | P0 | 为电脑常识问题提供可引用的解释证据 | 对已收录问题返回相关片段、出处和适用范围；缺少证据时返回证据缺口，不生成最终回答 |
| F-13 | P0 | 为购机需求匹配和候选比较提供证据 | 根据调用方已提供的预算、用途、便携等条件返回配置、取舍、适用人群和资料日期；条件不足时返回缺失条件 |
| F-14 | P0 | 为低风险故障自查和志愿者参考提供证据 | 返回下一步检查、目的、结果分支、停止条件和案例差异；不把相似案例当作确诊 |
| F-15 | P0 | 返回信息不足和转人工所需的结构化信息 | 返回设备、症状、已做检查、结果和待确认项；不补造现象、价格或故障原因，是否追问或转人工由调用方决定 |
| F-16 | P1 | 支撑社团学习和科普素材整理 | 根据主题整理概念、FAQ 和案例，保留引用及资料日期；输出可由成员继续编辑 |

以下保留面向业务的回答约束，供外部 Agent 集成时使用；知识库负责返回所需证据及其日期、条件和警告，首期不实现这些对话行为。

**购机咨询最低内容要求（外部 Agent）：**

- 用户已表达的硬约束必须保留，例如预算上限、系统要求或携带需求；没有满足条件的候选时明确说明。
- 只有在会改变推荐时才追问，例如主要软件／游戏、重量要求和购买时间，不要求所有用户填写完整问卷。
- 具体候选应说明型号、年份或可辨识配置、适用人群、优缺点和选择理由。已知参考价必须附带对应日期与条件。
- 对性能、续航、噪声等结论，区分规格推导与实际评测，不把不同测试条件下的数字直接比较。
- 无法支持具体型号或当前价格时，允许提供配置方向；不能把历史推荐包装成当前购买结论。

**维修辅助最低内容要求（外部 Agent）：**

- 先判断已有信息是否足够，再补充与问题有关的设备、系统、症状、发生时间、近期变化、重要数据和已做检查。
- 排查优先使用简单、低风险、尽量可恢复的检查。每个步骤说明检查目的、预期现象、不同结果如何影响下一步。
- 涉及数据修改、系统重装、拆机、固件更新等操作时，必须提示数据、保修及操作风险，并满足相应流程前提；首期面向普通用户的自查应转交志愿者处理此类操作。
- 对液体进入、明显烧焦味、电池鼓包等具有即时安全风险的现象，停止常规开机排查，提供简短的安全处置提示并转人工。
- 向志愿者提供专业材料时，展示适用条件和记录依据；不能仅因检索到同类故障就宣称已经确诊。

### 5.4 知识沉淀与反馈

| 编号 | 优先级 | 需求 | 可观察的验收条件 |
| --- | --- | --- | --- |
| F-17 | P1 | 支持维护者整理 FAQ、主题知识页与常见排查流程 | 后续实现时每项内容有维护者、适用条件、来源和版本；流程能表达前提、步骤、结果判断与停止条件；首期仅保留来源片段和结构化字段 |
| F-18 | P0（迭代四） | 接收错误、过时、无帮助等反馈，并关联查询、证据、来源及构建 | 迭代四成功保存 QueryRecord 后开放反馈；维护者能从反馈定位问题来源并修订；不要求保存生成回答，反馈和对话不会自动成为已验证知识 |
| F-19 | P1 | 辅助从维修记录生成案例、FAQ 或主题页草稿 | 保留原始证据和缺失信息；人工审核后才发布；来源更新时能识别受影响的草稿和知识页 |
| F-20 | P0 | 维护代表性问题集，记录检索和接口评估结果 | 能比较版本前后的检索相关性、来源定位和条件／状态返回；回答质量在外部 Agent 接入后另行评估 |

反馈与维修经验形成的业务闭环为：问题或维修记录 → 脱敏与补充 → 整理草稿 → 审核发布 → 检索使用 →（迭代四起）反馈修订。迭代一至三不保存 QueryRecord、不注册反馈端点，只返回 UUID query_id 和 `feedback_available=false`。对话保存与否由用户告知、权限和保存策略决定，不以“改进知识库”为由默认保留全部咨询记录。

### 5.5 受控自进化（P2 探索项）

自进化可以作为后续能力，指系统根据新资料和使用反馈主动发现问题、提出局部更新，再验证更新是否有效。演进对象包括知识、检索和流程，不包含根据原始对话自动训练模型。影响正式知识内容或回答行为的候选更新必须经过证据检查、离线评估、人工审核和版本发布；不合格时保持当前稳定版本。

F-06 的来源同步和 F-19 的辅助草稿生成仍是可独立采用的 P1 工具；本节 P2 能力是在这些工具基础上形成持续发现、提出、验证和采纳变更的闭环，不要求为已有工具提前建设完整自进化系统。

| 编号 | 优先级 | 需求 | 可观察的验收条件 |
| --- | --- | --- | --- |
| F-21 | P2 | 根据反馈、无结果查询、引用不匹配和已完成维修记录识别知识缺口 | 能生成待处理的问题或缺口列表，保留原问题、使用的知识版本和反馈；不会把反馈直接标记为事实 |
| F-22 | P2 | 从经授权和脱敏的资料中生成 FAQ、维修案例、术语别名或 Spec 草稿 | 草稿包含来源、缺失字段、适用条件和生成时间；未审核草稿不进入公开检索 |
| F-23 | P2 | 对候选知识、检索策略或流程变更执行自动检查和回归评估 | 检查引用支持、过期配置、权限泄露、危险维修建议和代表性问题集；评估不通过时不发布 |
| F-24 | P2 | 支持自进化变更的人工审核、版本发布和回滚 | 每次变更有变更原因、审核人、依赖来源和版本；发现问题能恢复到上一有效稳定版本，不能恢复已撤回的资料或已取消的权限 |
| F-25 | P2 | 在评估收益明确时优化检索词、分块、路由、提示或 Spec 规则 | 优化前后使用同一版本化评估集比较；不得绕过审核修改权限、安全边界或直接自动微调基础模型 |

建议的自进化闭环为：问题／维修记录 → 脱敏与结构化 → 识别知识缺口 → 生成候选草稿 → 规则检查与离线评估 → 成员审核 → 新版本发布 → 线上反馈与回滚。重复导入、元数据抽取、过期标记和候选关键词生成可以自动完成；由自进化生成或修改的维修步骤、购机结论、安全规则及其公开发布与权限变更，仍必须人工审核。此限制针对自进化候选，不要求首期已获准来源的正常导入逐篇人工审批。

自进化记录至少保留：用户问题或维修现象、意图与约束、检索结果、回答断言及引用、反馈、实际处理结果、候选变更、评估结果和审核决定。单次回答成功、用户表示“解决了”或模型声称完成，均不能单独作为知识发布依据。

数据记录沿用 N-04、N-05 的授权、脱敏和最少保存要求，缺失结果保留为未知。单次维修经验不自动升级为通用规则，模型整理的内容不能作为自身正确性的唯一证据；来源失效时，派生知识也需重新检查。

评估时区分用于提出和调整候选的开发问题与独立验收问题，记录知识、检索配置、模型版本及调用预算。每次更新既要检查目标问题是否改善，也要检查原有常识、购机和维修场景是否退化，并计入成员审核时间与模型成本。不能仅凭知识数量增加或同一批历史问题得分提升判断自进化有效；评估与审核规则由维护者管理，不由候选更新自行放宽。

## 6. RAG、知识图谱、LLM Wiki 与 Spec 的定位

这些技术可以配合使用，但不需要在首期全部引入。先明确知识服务应达到的效果，再根据评估选择实现方式。

本文将 **LLM Wiki** 暂定义为“由模型辅助整理、由成员审核维护的主题知识页”；将 **Spec** 暂定义为“以结构化方式记录的知识规则与操作／排查规范”。两者均为工作定义，不指代某个已经选定的开源项目；如果后续采用具体项目，需要重新对齐其能力与边界。

| 技术或组织方式 | 对应的需求价值 | 适用例子 | 建议采用方式与边界 |
| --- | --- | --- | --- |
| RAG（检索增强生成） | 从资料中取回证据，支撑有引用的回答 | 基础问答、检索评测与维修记录 | 首期建设检索与证据接口，兼顾语义与精确信息；回答生成属于外部 Agent |
| 知识图谱 | 显式管理实体和关系，辅助复杂关联查询 | 型号与配置、症状与检查、操作与前提之间的关系 | 首期可先维护必要的结构化字段和关联；复杂关联查询确有需求时再考虑图谱，不预设必须部署图数据库 |
| LLM Wiki | 把分散资料整理为稳定、易读、可维护的主题知识 | 新生购机指南、电脑维护 FAQ、常见蓝屏专题 | M6 / P1，首期暂不实现专门页面维护；后续再建设人工编辑与模型辅助草稿。主题页必须追溯原始证据，不能用模型摘要相互引用制造“多来源支持” |
| Spec | 明确适用条件、必问信息和操作步骤，使指导保持一致 | 购机约束检查表、无法开机排查流程、数据备份前提 | M6 / P1，首期暂不实现编辑与分支解释；首期保留来源已有步骤、前提和警告。后续规范需有来源、版本与审核 |

长期可分别管理三类内容：来源证据回答“根据是什么”，整理知识回答“如何理解”，流程规范回答“按什么条件和步骤处理”。首期实现来源证据层及必要字段；后续建设整理层与规范层时保持来源关联，规范或摘要与来源冲突时进入复核。

## 7. 非功能需求

### 7.1 质量、可维护性与运行要求

| 编号 | 维度 | 要求 | 验证方式 |
| --- | --- | --- | --- |
| N-01 | 正确性与证据一致性 | 返回证据与来源一致，区分确定事实、观点及推测；资料不足时返回证据缺口 | 代表性问题集人工复核片段相关性、适用条件与来源一致性 |
| N-02 | 可追溯性 | 从证据 ID 定位来源与构建、原文位置及审核、更新、停用记录 | 抽查引用查看接口及知识变更记录 |
| N-03 | 时效性 | 价格、推荐和软件版本敏感资料可标记过期；更新后片段和索引只使用当前构建；派生页面复核随 M6 后续建设 | 模拟文章更新、价格过期和文档撤回 |
| N-04 | 隐私与访问控制 | 维修记录中的姓名、学号、联系方式、账号信息、设备序列号及私人文件内容等按需要脱敏；授权范围贯穿检索、API 返回、引用和日志 | 使用含测试隐私标记的样本及不同角色验证不可见内容不被输出 |
| N-05 | 外部模型与资料安全 | 首期外部 embedding／reranker 调用符合数据使用范围；文档中的指令文本不能改变系统权限或发布规则；后续模型整理和外部 Agent 生成也遵循此约束 | 检查各模型调用的数据范围，并用含伪指令的资料验证处理边界 |
| N-06 | 可靠性与恢复 | 导入失败不能破坏已发布知识；服务失败能提示并重试；关键来源元数据、整理内容和配置可备份恢复 | 中断导入、模拟检索失败并进行恢复演练 |
| N-07 | 易用性 | 默认中文，保留常见英文硬件名称；维护者无需修改程序即可完成常规知识维护；接口字段和状态有说明 | 成员通过命令／维护 API 完成查找、导入、异常复核、修订和停用，调用方按说明使用 API |
| N-08 | 可维护与可移交 | 来源接入、知识维护和 Agent 调用的责任清晰；更换成员后仍可继续运营 | 有接入说明、字段说明、命令／API 操作及抽查与异常处理说明；可导出授权范围内的知识及来源关系 |
| N-09 | 可观测与可评估 | 可定位来源导入失败、知识过期、无结果和证据定位错误；保留必要的耗时与用量信息 | 查看问题记录与检索评估报告；首期可用简单日志和报表，不要求专门建设监控平台 |
| N-10 | 性能与成本 | 检索响应时间适合调用方使用；正常查询不需反复处理整个知识库；能区分导入处理与在线检索成本 | 在明确的数据量、并发量和检索模型条件下测试响应时间、失败率与单次成本 |

隐私默认要求：原始维修文本中非必要的个人信息不进入公开知识。日志优先保存查询标识、知识版本、错误和耗时，确需保存对话时应脱敏并明确保存期限。数据删除、备份保留和外部模型服务条款在上线前确定。

N-08 的首期工程约束包括：索引构建配置 `IndexProfile` 与查询运行配置 `QueryProfile` 分开标识，查询调参不触发无关的片段／向量重建，响应及 Trace 关联两类配置 hash；解析、编码、词法检索、重排和查询预处理通过少量稳定接口适配。采用模块化单体，不要求为每个模块建立独立服务或通用框架。

验证遵守项目单元测试规范：规则、字段校验、处理器替换和回退用单元／离线契约测试；事务、权限过滤和持久化用真实 PostgreSQL 集成测试；检索效果和每阶段独立运行另做实际链路验收。单测通过不替代模型质量、性能或权限专项验收。

### 7.2 首期建议验收指标

以下是供首期讨论的目标值，**不是现有系统成绩或对真实用户流量的承诺**。在数据抽样后确认口径；评估时记录资料版本、模型版本和测试环境。

| 指标 | 建议目标 | 口径与限制 |
| --- | --- | --- |
| 检索命中率 | ≥ 90% | 在已有正确资料且人工标注了依据的问题中，前 5 条检索结果包含至少一项能支持核心回答的有效证据；无答案问题单独统计 |
| 证据追溯专项 | 验收用例全部通过 | 返回的证据 ID、来源、构建和原文位置可核查；引用查看再次检查权限和撤回状态 |
| 时效与配置专项 | 验收用例全部通过 | 旧价格不作为当前价格，不将不同年份／配置的参数混用；没有当前证据时明确限制 |
| 隐私与维修风险信息专项 | 验收用例全部通过 | 不输出测试隐私标记和无权内容；返回的步骤保留来源中的适用前提、警告和停止／转人工条件。通过有限用例不等于不存在其他风险 |
| 检索响应时间 | P95 ≤ 2 秒 | 建议先以 1000 篇文本资料、5 个并发查询试测，包含在线 embedding 和启用的重排；记录总文本量与检索单元数 |
| 使用成本 | 可测量、有预算上限 | 记录单次检索及批量导入的用量和估算成本；预算由社团确认，不预设金额 |

首期建议准备至少 60 个代表性问题，常识、购机、维修各至少 15 个，其余覆盖信息不足、证据缺失、过期、冲突和权限等情况。问题优先来自真实咨询并脱敏，标明预期依据与可接受结果；保留一部分问题用于调整后的独立验收，避免只评估反复调优的样本。需要多项证据才能完成的问题，应人工检查全部关键依据是否召回。

### 7.3 外部 Agent 集成后的业务评估

以下目标保留作整体业务参考，由外部应用接入生成模型后验证，不作为知识库首期交付条件：

| 指标 | 建议目标 | 口径与限制 |
| --- | --- | --- |
| 回答可接受率 | ≥ 85% | 人工检查准确性、适用性、清晰度和任务完整性，分别报告常识、购机、维修三类结果 |
| 回答引用支持率 | ≥ 95% | 检查关键断言是否确实被引用证据支持，同时检查本应引用却未引用的参数、价格和维修结论 |
| 完整回答响应时间 | P95 ≤ 20 秒 | 包含知识检索和模型生成；按实际模型资源、预算与外部应用方案确认 |

## 8. 核心验收场景

A-01～A-14 验收知识库 API 的证据和状态，不要求开发聊天入口或接入生成模型；外部 Agent 的最终回答另按第 5.3、7.3 节验证。

| 编号 | 前提与用户操作 | 应观察到的结果 | 对应需求 |
| --- | --- | --- | --- |
| A-01 | 用户询问已收录的内存与硬盘区别 | 返回解释所需的片段和可核查来源，不足时返回证据不足状态 | F-07、F-10、F-12 |
| A-02 | 用户只说“推荐一台电脑” | 返回预算、用途等缺失条件，可附通用选购资料；不将候选标为已满足未知条件 | F-13、F-15 |
| A-03 | 用户给出预算、软件和便携要求，库中有合适的近期资料 | 返回符合已知硬约束的配置及相关取舍、适用人群、资料日期证据 | F-08、F-13 |
| A-04 | 用户询问当前购机，库中只有旧推荐和旧价格 | 明示日期与信息不足，不声称当前最低价或当前最优机型 | F-09、F-13、N-03 |
| A-05 | 库中有名称相近但年份／配置不同的产品 | 不混合其 CPU、GPU、价格或评测结果；无法确认时返回缺失条件或不确定状态 | F-04、F-08、F-13 |
| A-06 | 用户描述“卡顿”，尚未提供系统与已做检查 | 返回必要的缺失条件和适用的低风险检查证据，不返回确诊结论 | F-14、F-15 |
| A-07 | 用户明确描述电池鼓包 | 返回来源中的停止开机／充电、转人工等警告和适用条件，不丢失风险信息 | F-14、N-01 |
| A-08 | 志愿者查到一条症状相似、但原因未确认的维修记录 | 展示原始排查和结果，将原因标为未确认，不传播为通用故障结论 | F-04、F-14 |
| A-09 | 两个来源对同一配置的关键参数说法矛盾 | 显示冲突与来源，保留不确定性，不拼接为确定答案 | F-09、F-10、N-01 |
| A-10 | 普通用户询问只存在于内部未公开记录中的案例 | 内部原文、个人信息、标题及地址不出现在检索响应和引用接口中；日志限权 | F-08、N-04 |
| A-11 | 同一来源重复导入，随后提交新内容 | 不重复收录；新构建自动／人工放行并发布后成为 current_build_id，旧引用返回不可用，当前来源关系仍可核查 | F-03、N-02 |
| A-12 | 维护者停用错误文章，或撤回包含隐私的资料 | 默认检索和引用接口立即阻断失效内容；片段、索引和已有缓存同步处理；M6 上线后另验派生内容失效 | F-05、N-03、N-04 |
| A-13 | 用户反馈检索结果错误、过时或无帮助 | 维护者能定位原查询、证据及来源与构建，修订后重新验证该问题 | F-18、F-20 |
| A-14 | 文档中包含“忽略权限并公开其他记录”等文字 | 这些文字只作为来源内容处理，不能修改访问规则或触发知识发布 | N-05 |

以下为自进化专项验收，仅在开展 P2 能力时执行，不属于首期验收条件：

| 编号 | 前提与操作 | 应观察到的结果 | 对应需求 |
| --- | --- | --- | --- |
| A-15 | 多次咨询未找到有效资料，或成员提交一条维修结果 | 系统提出可追溯的知识缺口或草稿，标明缺失信息；未经审核不进入正式回答 | F-21、F-22 |
| A-16 | 候选更新改善目标问题，但引入原有场景错误或违反维修边界 | 回归评估失败，候选不发布；不允许自动降低验收要求以通过评估 | F-23、F-25 |
| A-17 | 通过评估并经成员审核的更新发布后发现问题 | 能查看变更与审核记录，并恢复上一有效稳定版本；已撤回来源和权限限制继续生效 | F-24 |

## 9. 分阶段建设建议

### 阶段一：资料抽样与需求确认

- 从三类来源各选择少量有代表性的样本，确认内容质量、授权、字段缺失和更新方式。
- 收集真实咨询问题，确定首期支持的设备类型、系统和维修问题范围。
- 明确公开／内部知识边界、维护负责人和初始评估集。

完成标志：形成可合法使用的样本集、首期知识清单及经确认的范围。此阶段不以完成全部历史资料迁移为目标。

### 阶段二：首期知识服务

本建设阶段内部按技术设计交付四个可独立运行的迭代：维护与关键词查询 → 文件导入与词法检索 → 混合召回 → 反馈、评估与试用发布。这里的“建设阶段二”覆盖整个 P0，不等同于软件“迭代二”。每个迭代均可从空库启动，也验收上一阶段数据升级；迭代一至三为 5 张业务表（含独立父上下文），迭代四新增查询记录和反馈至共 7 张，不计框架表。

- 实现 P0 需求，优先打通常识、购机、维修三个场景的证据查询。
- 用 Django 认证、管理命令和 DRF 知识查询／维护 API 完成维护；Django Admin 按需启用，不作为首期必需交付。数据库工具采用只读访问，用于查看和排查。
- 以 Python 模块化导入流程、PostgreSQL 任务表和单 Worker 完成导入、自动校验／异常复核、统一发布与检索引用；迭代四再增加 QueryRecord、反馈和评估闭环。
- 用 API 测试客户端和代表性问题集验收，再面向少量成员或获授权客户端试用；M6 与 Agent 开发不作为本阶段前提。

完成标志：各迭代均可独立运行；最终迭代的主要场景有可核查的评估结果，隐私、配置、时效和维修边界专项通过，成员能够完成日常维护和反馈处理。

### 阶段三：依据问题增强

- 按问题集结果引入 F-26 静态场景检索偏好，优先验证维修案例／流程和购机规格／推荐的效果，保留通用检索及策略回退。
- 有跨来源知识整理需求时，再建设 M6 的 FAQ／主题页／Spec 编辑及派生证据依赖管理。
- 维护工作量过大时，增加授权来源同步与模型辅助草稿生成；编排复杂度上升时再评估 Haystack。
- 关联查询效果不足时，补充结构化关系或知识图谱。
- 维修引导一致性不足时，扩展 Spec／排查流程；资料覆盖不足时，优先补齐来源。
- 每项增强都与现有方案比较效果和维护成本，不以引入技术种类数量作为完成标准。

### 阶段四：受控自进化探索（可选，P2）

- 在基本知识服务稳定、已有可用反馈与评估集且成员具备审核时间后，再决定是否启动，不影响前述阶段交付。
- 先围绕一个高频知识缺口验证 F-21 至 F-24 的闭环，再按收益考虑 F-25 的检索或流程优化；不要求同时演进所有组件。
- 启用条件包括明确维护负责人、试验范围、评估标准及运行成本上限；效果不明显时可以停止试验，继续使用人工维护流程。

完成标志：候选更新可追溯、可评估、经审核后发布且可回滚；有独立评估说明实际收益和维护成本，不以更新次数或新增知识量作为成功标准。

| 对话、日志、原始维修记录保存多久？ | 只保存维护与评估必要的数据，默认脱敏 | 影响隐私告知、删除和备份策略；采集真实用户数据前确定 |
