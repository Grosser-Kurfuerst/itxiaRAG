# 机型规格库实施记录

按时间顺序记录[机型规格库方案](product-spec-design.md)各步骤的实施过程，以及推荐评测和上层 LLM 模拟评测的结果。
- 指标定义与各阶段验收见[方案第 8 节](product-spec-design.md#8-评测设计)与[第 9 节](product-spec-design.md#9-分阶段迭代计划)。
- D 类标注变化引起的召回回归记在[召回评测第 9 节](../phase1/yuque-ingestion/retrieval-evaluation.md#9-初步评测执行记录)，基线变化记在[召回改进记录](../phase2/retrieval-improvement-log.md)。
- 运行命令见[维护手册 8.1](../maintenance.md#81-运行与对比)，结果文件放在被忽略的 `.runtime/eval/corpus-v5/` 下，不提交。

## 1. 推荐评测（P1.5，2026-10-12）

方案 P1.5 新增推荐评测脚本 [recommend_eval.py](../../eval/recommend_eval.py) 与软条件查询集 [recommend-queries.json](../../eval/recommend-queries.json)。同一步把 D 类标注改为读取规格文件，召回回归见[召回评测 9.13](../phase1/yuque-ingestion/retrieval-evaluation.md#913-d-类改读规格文件p152026-10-12)。

- **链路**：D 类 18 条条件查询的标准条件由评测器换算成原子条件（轻薄 → `weight_max` 1.5，接口丰富 → `usb_a`、`usb_c`、`video_out`，OLED → `panel`），调用推荐服务、按日期排序。18 条的推荐集合都与标注答案集合完全相同（`top_k` 取 20，覆盖最多 18 台的答案），P@5 全部为 1，说明过滤与标注口径一致。这一项只证明链路正确（方案 8.1 的自证问题）。nDCG@5 平均 0.912，答案少于 5 台时理想排序含“只差一条条件”的机型，推荐结果不含这些机型，所以小于 1。
- **软条件排序**：6 条新查询 S01～S06 加 D01、D04，条件为原子条件，`grades` 按评测原文的测试数据分级（双烤功耗、满载噪音、最大亮度、色域、续航与面板、接口种类，规则写在每条查询的 `basis` 中，未列出的机型为 0）。

  | 查询 | 只按日期 | 按 preference |
  | --- | --- | --- |
  | S01 一万以内性能释放强的游戏本 | 0.46 | 0.76 |
  | S02 续航长、屏幕好的轻薄本 | 0.31 | 0.80 |
  | S03 一万以内噪音小的游戏本 | 0.23 | 0.56 |
  | S04 6000 元以内色域广、适合修图 | 0.00 | 0.68 |
  | S05 一万以内屏幕亮度高的游戏本 | 0.00 | 0.21 |
  | S06 接口丰富的轻薄本 | 0.06 | 0.25 |
  | D01 一万以内轻薄、性能释放强的游戏本 | 1.00 | 0.63 |
  | D04 用石墨烯导热的游戏本 | 0.00 | 1.00 |
  | 平均 | 0.257 | 0.612 |

  按 `preference` 排序明显优于只按日期，保留现有设计：有 `preference` 时按检索名次排序，为空时按评测日期由新到旧。比较数值高低的偏好（S05 亮度、S06 接口种类）提升有限，检索只能匹配“亮度”“接口”等描述，不能比较实测数值。D01 只有 3 台候选，日期排序恰好把唯一的 2 级机型排在第一。
- **结论附带率**：78 篇评测都有结论栏目子块，兜底取最后一个子块的为 0 篇。

结果为 `.runtime/eval/corpus-v5/recommend-v1.json`，不提交。

## 2. 上层 LLM 模拟评测脚本（P3.2，2026-10-13）

[机型规格库方案](product-spec-design.md) P3.2 新增了 [llm_eval.py](../../eval/llm_eval.py)。脚本用一个 OpenAI 兼容的对话模型，加上[工具定义](../../products/tool-definitions.md)中的提示词和两个工具，模拟上层系统，评测[方案 8.2 节](product-spec-design.md#82-各阶段指标)的三项 P3 指标：

- **工具选择**：在 170 条查询上检查第一轮调用的工具。D 类应只选机型推荐，其余类别应只选知识检索。同一轮同时调用两个工具算选错。
- **条件换算**：对 D 类 18 条有标准条件的查询，逐条列出 LLM 给出的原子条件与标准条件的差异。数值保留两位小数比较，列表不计顺序。
- **端到端**：按 LLM 给出的参数调用推荐服务，计算 P@5 和 nDCG@5，按两个口径报告：
  - D 类全部 19 条，与 v17 的 0.311／0.436 对比；
  - 有标准条件的 18 条，与链路结果对比，差值即 LLM 理解问题带来的损失。

**补充样例** [llm-queries.json](../../eval/llm-queries.json) 包含 7 条口语化查询和 4 组多轮追问。

- 口语化查询用的说法（如“背着不累”“打游戏不卡”“大学生笔记本”）都不在提示词的参考口径里。
- 多轮追问覆盖三种情况：追加条件、撤销条件、追问候选机型的细节。
- 多轮样例中，助手回合用文字摘要代替真实的工具调用与工具结果，这是一种简化。
- 每条样例都按参考口径给出标准原子条件，答案为满足标准条件的全部机型。

**脚本约定**：

- 只看 LLM 第一轮回复的工具调用，不执行多步对话。
- 推荐统一取前 20 台，忽略 LLM 给出的 `top_k`。
- 参数不合法时记为参数错误，不重试，端到端记为 0。参数不合法包括：参数不是 JSON 对象、条件平铺到顶层、未知条件、取值不在可选范围内。
- 未调用推荐工具的 D 类查询，端到端记为 0。
- 结果 JSON 保存完整的工具调用，以及模型名、工具定义的 sha256 和补充样例版本，供修订前后对比。

提示词和工具定义中的示例刻意避开了查询集原文。但工具定义的参考口径与 D 类标准条件同源，换算一致是预期结果。

D01 是例外。它的标准条件是 `weight_max` 2.3 加显卡档次，而参考口径会把“轻薄”换算为 1.5、把“性能释放强”写进 `preference`，照口径换算会得到空结果。分析 D01 的差异时，应先归为口径冲突。第 4 节已把 D01 的标准条件改为与参考口径一致。

**验证状态**：评测链路先用替身验证，真实模型的运行结果见第 4 节。

- 不联网检查：替换 `urlopen` 后，验证了请求地址与认证头，以及以下几类回复都会按约定记录：参数为空串或 null、非法 JSON、条件被编码成字符串、条件平铺到顶层、直接回答。
- 正式库全流程：替身直接返回标准答案。D 类返回标准条件；D04 返回 `is_gaming` 加 `preference`“石墨烯导热”；其余查询返回知识检索。其中有意把 D01 写成 `thin_light`，用来验证错误路径。结果如下：
  - 工具选择 170/170；
  - 条件换算一致 17/18，D01 记为参数错误；
  - 端到端：19 条的 P@5 为 0.947、nDCG@5 为 0.870；18 条的 P@5 为 0.944、nDCG@5 为 0.862；
  - 链路：P@5 为 1.000、nDCG@5 为 0.912，与第 1 节相同；
  - 补充样例：工具选择 11/11，条件一致 9/9，P@5 为 1.000。

## 3. 规格文件补齐 CPU、内存与硬盘（P2.3，2026-10-13）

外部 LLM 按[维护手册的规格填写](../maintenance.md#规格填写)为 78 台补齐 `cpu`、`ram_gb`、`ram_upgradable`、`storage_gb` 及原文引用，并为原先没有价格的 ROG 枪神10 Plus 联网补了 RTX 5080 版首发价 29999 元（2026-05-22 报道，已核对链接）。全部引用通过 `import_specs` 校验，值与引用逐台一致。

- **召回评测（v18）**：枪神有了价格后满足 D13“两万以上的顶级游戏本”，答案从 9 台变为 10 台，查询集升为 v7，见[召回评测 9.14](../phase1/yuque-ingestion/retrieval-evaluation.md#914-规格文件补齐后的召回回归p232026-10-13)。
- **推荐评测**：链路集合 18/18 相同，D13 的推荐集合含枪神；P@5 1.000、nDCG@5 0.912，软条件排序 0.257／0.612，结论附带 78/78，均与第 1 节相同。

结果为 `.runtime/eval/corpus-v5/recommend-v2.json`，不提交。

## 4. 真实模型运行与工具定义修订（P3.2、P3.3，2026-10-14）

用 DeepSeek 官方接口的 deepseek-flash 运行第 2 节的脚本，修订前后各跑一次。

**修订前（llm-v1）**：

- 工具选择 169/170。D06“支持TGX接口外接显卡的笔记本”调用了两次知识检索，没有调用推荐。
- 条件换算一致 14/18：
  - D01 照参考口径换算（轻薄 1.5kg，“性能释放强”写进 `preference`），与标准条件（2.3kg 加显卡档次）冲突，推荐结果为空；
  - D06 未调用推荐，提示词没有说明 TGX 即 OCuLink；
  - D09、D15 句中还有其他条件时，把“预算 X”换算成了“X 以内”，而同样说法的 D08 换算正确。
- 端到端：D 类 19 条 P@5／nDCG@5 为 0.863／0.796（v17 为 0.311／0.436）；有标准条件的 18 条为 0.856／0.784，链路为 1.000／0.912。
- 补充样例：工具选择 10/11（L05 同一轮同时调用推荐与知识检索），条件一致 9/9，P@5 1.000。

**修订（P3.3）**：

- 提示词的参考口径：
  - “预算 X”和其他条件一起出现时也按 0.75X～1.1X 换算，不等于“X 以内”；
  - 增加“轻薄游戏本：`weight_max` = 2”；
  - 增加“TGX 接口即 OCuLink”，`ports` 的字段说明同步补充。
- D01 标注：
  - 查询改为“一万五以内、机身轻薄、性能释放强的游戏本”，标准条件改为游戏本、15000 元以内、2.0kg 以内，去掉显卡档次。
  - “性能释放”无法从规格换算：评测正文中功耗的测试项目、性能模式和写法都不统一，只有 18 篇给出了双烤功耗。因此留在 `preference`，不新增规格字段。
  - 2kg 以内的游戏本只有 5 台，且都超过一万，所以预算一并放宽，答案为 4 台。
  - 查询集因此升为 v8。
- 软条件排序集中同名的 D01 是独立样例，自带条件和人工评分，保持不变。

**回归（v19、recommend-v3）**：

- 召回（v19）：新 D01 的答案排第 1，`all` 范围混合 Hit@1／Hit@5／MRR@10 为 0.78／0.95／0.857，见[召回评测 9.15](../phase1/yuque-ingestion/retrieval-evaluation.md#915-d01-标注修订后的召回回归p332026-10-14)。
- 推荐：链路集合 18/18 相同，P@5 1.000、nDCG@5 0.915（D01 为 0.95）；软条件排序 0.257／0.612、结论附带 78/78 不变。

**修订后（llm-v2）**：

| 指标 | 修订前 v1 | 修订后 v2 |
| --- | --- | --- |
| 工具选择 | 169/170 | 166/170 |
| 条件换算一致 | 14/18 | 16/18 |
| D 类 19 条 P@5／nDCG@5 | 0.863／0.796 | 1.000／0.922 |
| 有标准条件的 18 条 P@5／nDCG@5（链路） | 0.856／0.784（0.912） | 1.000／0.918（0.915） |
| 补充样例：工具选择、条件一致、P@5 | 10/11、9/9、1.000 | 11/11、8/9、1.000 |

- D01、D06、D09、D15 的换算全部一致。D01 的标注也改了，v1 与 v2 的 D 类指标同时包含标注变化。
- LLM 的 nDCG@5 略高于链路：链路按日期排序，LLM 多数给出了 `preference`。
- 剩余的条件差异都不影响推荐集合：
  - D12“预算一万左右”换算为 7500～11000，标准为 9000～11000；
  - D16 多加了 `screen_max` 16.1；
  - M03“算了不要游戏本”加了 `is_gaming` = false，比标准条件更贴近原意。
- 工具选择的 4 处选错都是同一轮同时调用两个工具：C02、F10 用推荐定位“那台”机型，G03 资料中没有对应机型，D04 在推荐之外另检索“石墨烯”。本次修订没有涉及工具选择的说明，先按单次运行的波动记录，暂不修订。

两次运行都只跑了一次，模型也是轻量模型。上层系统换用其他模型时结果会不同，正式效果以上层系统自己的评测为准。

结果为 `.runtime/eval/corpus-v5/llm-v1.json`、`llm-v2.json`、`recommend-v3.json`，不提交。
