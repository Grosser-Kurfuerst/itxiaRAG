# 技术方案：机型规格库与按条件推荐

本文给出机型规格库的设计与分阶段迭代计划，对应[第三阶段需求](requirements.md) F2-07（选购条件解析）与 F2-08（评测结构化属性）。**状态：方案，未实施（2026-10-12）。**

## 1. 背景与结论

v16 基线（[评测 9.11](../phase1/yuque-ingestion/retrieval-evaluation.md#911-池化补标与新基线f2-012026-10-12)）中，问单台机器配置的查询效果稳定，按条件找机器是最弱项：

| 场景 | 类别 | 混合 Hit@1／Hit@5／MRR@10 |
| --- | --- | --- |
| 问某台机器的属性 | A、B、E、F（28 条） | 全部 1.00／1.00／1.000 |
| 口语化问属性 | C（5 条） | 0.60／1.00／0.800 |
| 按条件找机器 | D（19 条） | 0.32／0.63／0.446；P@5 0.311、nDCG@5 0.436 |

D 类失败的原因是检索只能字面匹配，不理解价格、重量、续航区间（D17、D20 的 P@5 为 0），组合条件在召回阶段就丢失（D14、D19 混合前 20 名无答案），知识文档还会挤进前 5 名。调整分段和融合参数解决不了这类问题。

**方案**：

- 建立机型规格库，新增独立的推荐接口。硬条件用 SQL 过滤，软条件在候选机型的评测原文中检索排序。每台推荐机型同时返回规格和笔吧评测的结论、评语原文。
- **理解问题全部交给上层接入的 LLM**，包括判断问题类型、选择调用哪个接口、把用户的说法换算成结构化条件。检索系统不做意图识别和条件解析，线上链路不依赖 LLM。职责划分见第 3 节。
- **规格数据由人工或外部 LLM 填写。** 项目内不实现规格提取，维护手册给出填写规则与示例，导入时校验原文引用（第 7 节）。

**可行性依据**：[eval/attributes.json](../../eval/attributes.json) 已是规格库的原型。它覆盖 78 台机器，记录了价格、重量、屏幕、OLED、独显、续航和 8 类接口，从评测原文半自动提取后人工核对，D 类正确答案就是按它生成的。

## 2. 范围

检索系统做：

- 机型规格表，与评测父段一一关联。
- 规格数据文件与导入命令，导入时校验原文引用。
- 评测子块记录所属小节，用来取出评测结论。
- 推荐接口：按原子条件过滤、按软条件文本排序，返回规格与评测原文。
- 两个接口的工具定义，供上层 LLM 调用。
- [维护手册](../maintenance.md#规格填写)中的规格填写规则与示例，供人工或外部 LLM 使用。

检索系统不做：

- 问题类型判断、选购条件解析、口语说法到数值的换算。这些由上层 LLM 完成，见第 3 节。
- 规格自动提取。项目内不调用任何对话模型。
- 评测原文变化的过期检测。公众号文章发布后基本不变，重新采集时由维护者自行核对。
- 回答生成、多轮对话、追问用户。
- 价格抓取与更新。只记录评测时的价格和日期。
- 条件筛空后自动放宽。只报告是哪个条件筛掉了全部机器。
- 型号与配置的层级、通用属性表（EAV）、属性变更历史。
- 把推荐结果与混合检索做 RRF 融合。两者是独立接口。

## 3. 职责划分：上层 LLM 与检索系统

上层系统指接入本知识库、负责与用户对话并生成回答的应用，例如社里的问答机器人，不在本仓库中实现。它把检索系统的两个接口作为工具（function calling）调用：

| 工具 | 接口 | 用途 |
| --- | --- | --- |
| 知识检索 | `POST /api/v1/search/`（现有，不变） | 问具体机型的配置与表现、教程、知识、工具、维修 |
| 机型推荐 | `POST /api/v1/products/recommend/`（新增） | 按条件找机器 |

### 3.1 上层 LLM 负责

| 职责 | 说明 | 示例 |
| --- | --- | --- |
| 判断问题类型，选择工具 | 决定调用知识检索、机型推荐，还是两者都调 | 问“来酷 GT 16 多重”用知识检索；问“一万以内的游戏本”用机型推荐；问“8000 左右的轻薄本，能自己加内存吗”可以先推荐，再对候选机型做知识检索 |
| 把说法换算成原子条件 | 推荐接口只接受原子条件（5.2），所有换算都由 LLM 完成。工具说明中给出参考口径（3.3），LLM 可以按语境调整 | “轻薄”→ `weight_max: 1.5`；“预算 8000”→ `price_min: 6000, price_max: 8800`；“5070 以上”→ `gpu_in: ["RTX 5070", "RTX 5070Ti", "RTX 5080", "RTX 5090"]`；“能接网线”→ `ports: ["rj45"]` |
| 提炼软条件 | 无法结构化的诉求作为 `preference` 文本传给推荐接口 | “性能释放强”“散热好”“屏幕素质好” |
| 继承多轮上下文 | 后续追问在之前条件的基础上修改 | 上一轮“8000 左右的轻薄本”，这一轮“有没有便宜点的”→ 下调 `price_max` 后重新调用 |
| 处理推荐结果 | 结果为空时，根据 `diagnostics` 放宽条件或反问用户；根据 `unknown` 说明有机型缺少数据；条件不足时先反问 | “预算多少？”“另有 3 台没有续航数据” |
| 生成回答 | 引用规格和评测原文作答；价格注明是评测时的价格，并给出评测链接 | — |

### 3.2 检索系统负责

| 职责 | 说明 |
| --- | --- |
| 执行原子条件 | 按条件过滤，空值一律不满足，遵守可见范围 |
| 软条件排序与取证 | 在候选机型的评测原文中按 `preference` 排序，返回结论子块与命中子块 |
| 报告结果状态 | 统计因缺数据被排除的机型（`unknown`）；结果为空时给出各条件单独满足的机型数（`diagnostics`） |
| 校验与格式规范化 | 校验类型与范围；显卡型号统一大小写和空格（“RTX 5070 Ti”→“RTX 5070Ti”）；未知的显卡型号或品牌返回 400，并附上可选值，便于 LLM 修正后重试。这里只统一写法，不换算语义 |
| 维护规格数据 | 规格文件与导入命令；填写规则与示例写在维护手册中 |
| 提供工具定义 | 两个接口的参数、单位、取值范围、参考口径和调用示例，见 3.3 |

### 3.3 工具定义

工具定义放在 `products/tool-definitions.md`，给出可以直接放进 function calling 的 JSON Schema 和文字说明。内容包括：

- 每个参数的含义、单位、空值语义，例如“续航只指日常应用仿真成绩，许多机型没有该数据”。
- 可选值：显卡型号、品牌，由规格文件生成。
- 参考口径，沿用[评测 4.2 节](../phase1/yuque-ingestion/retrieval-evaluation.md#42-标注格式)：

  | 说法 | 参考换算 |
  | --- | --- |
  | 轻薄 | `weight_max: 1.5` |
  | 接口丰富 | `ports: ["usb_a", "usb_c", "video_out"]` |
  | 预算 X | 0.75X～1.1X |
  | X 以内／X 左右／X 多／X 以上 | ≤X ／ 0.9X～1.1X ／ X～X+999 ／ ≥X |
  | 游戏本 | `is_gaming: true` |
  | 显卡 N 以上 | 显卡档次表中不低于 N 的型号 |

- 选择工具的说明：何时用知识检索、何时用机型推荐、何时两者都用。
- 调用示例，包括结果为空后放宽条件的示例。

参考口径只是建议，检索系统不强制执行。上层 LLM 实际换算得是否一致，由 P3 的评测脚本衡量（7.2）。

### 3.4 这样划分的理由

- **上层 LLM 掌握的信息更全。** 多轮对话的条件继承只有在上层才能做，检索系统只看到单条请求。
- **调用更灵活。** 可以组合多次调用、放宽条件、反问用户，检索系统内部做不了这些。
- **检索系统保持确定、可测。** 不增加 LLM 依赖和延迟，不会把配置类问题误分流到推荐，问题也不经检索系统外发。
- **不重复调用模型。** 上层生成回答本来就要调用 LLM，不需要检索系统再调一次。

代价是条件换算的一致性不再由检索系统保证，相同说法在不同调用中可能换算出不同区间。这部分由工具定义中的参考口径和 P3 评测来约束。

## 4. 总体架构

```text
用户 ⇄ 上层系统（LLM：判断问题、换算条件、生成回答）
          ├─ 知识检索工具 → POST /api/v1/search/ → 现有混合检索（不变）
          └─ 机型推荐工具 → POST /api/v1/products/recommend/
                              → products.RecommendationService
                                  ① products.selectors：SQL 按原子条件过滤 → 候选机型
                                  ② 复用 MultiRouteRecall + PostRecallPipeline，范围限定为候选机型的评测父段 → 按 preference 排序
                                  ③ 读取规格卡、评测结论子块、软条件命中子块

维护：评测正文 → 人工或外部 LLM 按维护手册的规则填写 → 人工核对 → 规格文件 → import_specs（含引用校验）→ product_spec 表
```

| 模块 | 责任 | 不负责 |
| --- | --- | --- |
| `products/`（新增） | 规格表、规格文件导入、条件过滤、推荐编排、工具定义 | 召回算法、条件换算、规格提取 |
| [contracts/](../../contracts/) | `ProductFilter` DTO、推荐请求 Serializer、`Recommender` 协议 | 实现 |
| [catalog/](../../catalog/) | `scoped_contexts` 增加按父段过滤 | 规格数据 |
| [api/](../../api/) | 新增推荐接口，与现有接口共用认证与可见范围 | 推荐逻辑 |
| [config/components.py](../../config/components.py) | 注入推荐服务 | 业务规则 |

依赖方向：`products` 依赖 `catalog` 和 `contracts`。推荐服务通过协议使用召回器与流水线，不直接导入 `retrieval`。[retrieval/service.py](../../retrieval/service.py) 的 `search()` 不改动。

## 5. 数据设计

### 5.1 规格表 `product_spec`

一行是一台评测过的具体配置，与评测父段的粒度一致。同系列不同配置是不同的行，例如战 7000P 和战 7000P 锐龙版。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `key` | 文本，唯一 | 机型身份。有评测的机型等于评测的 `entity_title`（如“联想 来酷GT 16 酷睿版”） |
| `brand` | 文本 | 品牌，供“联想的轻薄本”这类条件使用 |
| `review_context` | 一对一关联 `ContextUnit`，可空，删除时置空 | 评测父段。没有评测的机型为空 |
| `price_cny` | 数值，可空 | 评测给出的售价 |
| `price_kind` | 枚举，可空 | `launch` 首发价、`reference` 参考价、`subsidy` 补贴价、`predicted` 预测价 |
| `price_date` | 日期，可空 | 价格对应的日期，默认是评测日期 |
| `weight_kg` | 数值，可空 | 机身重量。二合一产品是否含键盘，写在 `note` 中 |
| `screen_inch` | 数值，可空 | 屏幕尺寸 |
| `panel` | 枚举，可空 | `oled`、`lcd`、`miniled` |
| `cpu` | 文本，可空 | 处理器型号 |
| `has_dgpu` | 布尔，可空 | 是否有独显 |
| `gpu` | 文本，可空 | 独显型号，写法统一为“RTX 5070Ti” |
| `ram_gb`、`ram_upgradable` | 整数、枚举，可空 | 内存容量；`slots` 有插槽、`soldered` 板载 |
| `storage_gb` | 整数，可空 | 硬盘容量 |
| `battery_hours` | 数值，可空 | 只记“日常应用仿真”脚本的成绩 |
| `is_gaming` | 布尔，可空 | 游戏本定位：有 RTX 独显，定位为创作本或双屏本的除外 |
| `ports` | JSONB | 8 个布尔键：`usb_a`、`usb_c`、`video_out`、`hdmi`、`rj45`、`card_reader`、`thunderbolt`、`oculink` |
| `ports_text` | 文本 | 评测原文的接口段落 |
| `extra` | JSONB | 不参与过滤的属性，如刷新率、分辨率、噪音、双烤功耗 |
| `evidence` | JSONB | `{字段名: 引用}`，可选。来自评测原文的值为引用字符串，导入时校验它出现在评测正文中；联网补充的值为 `{source, quote}`，由人工核对 |
| `note` | 文本 | 计价口径等说明，如“按键盘 + 笔套装计价与重量” |
| `updated_at` | 时间 | 最后导入时间 |

规则：

- **空值表示“未知”**，不表示“没有”。v16 语料中 78 台有 31 台缺少日常续航成绩。
- **只存原始数值，不存派生概念。** 例如存重量，不存“是否轻薄”。派生概念由上层 LLM 换算（3.1）。`is_gaming` 例外，定位本身就是一个标签，无法由其他字段推出。
- **规格文件中的条目都视为已审核。** 草稿留在维护者本地，不进规格文件。
- **可见范围**：有评测的机型跟随评测来源的 `visibility`。没有评测的机型来自官网参数等公开资料，视为 `public`。

现有 attributes.json 的字段与本表的对应关系：

| attributes.json | product_spec | 转换 |
| --- | --- | --- |
| `price` | `price_cny`、`price_kind` | `price_kind` 按 `note` 判断（如“原文为预测售价”→ `predicted`），其余为 `reference` |
| `weight`、`screen`、`battery_hours`、`ports`、`ports_text`、`note` | 同名字段 | 直接复制 |
| `oled` | `panel` | `true`→`oled`，`false`→`lcd` |
| `gpu` | `has_dgpu`、`gpu` | `null`→`has_dgpu: false`（原表中 `null` 表示核显） |
| `gaming` | `is_gaming` | 直接复制 |
| `entry` | — | 只用于核对关联 |
| — | `brand` | 取 `entity_title` 的第一个词 |
| — | `cpu`、`ram_*`、`storage_gb`、`extra`、`evidence` | 留空，之后按维护手册补齐 |

### 5.2 与评测父段的关联

单机评测父段的 key 由 `entity_title` 的哈希生成（[strategies.py:30](../../ingestion/strategies.py)）。重新导入时父段按 key 原地更新（[storage.py:45](../../catalog/storage.py)），所以外键不会失效。多机型文章按 `entity_headings` 切成多个父段，每台机器仍然对应一个父段。

导入规格时，在 `product_review` 父段中按 `ContextUnit.title == key` 查找，必须恰好找到 1 个，做法与评测器的 [resolve_alias](../../eval/recall_eval.py) 相同。找不到时，通常是维护时改了 `entity_title` 或评测已下线：外键置空，机型不参与推荐，导入报告列为“失去关联”。

### 5.3 规格数据文件

规格数据的源头是提交到仓库的 `products/specs/bibar.json`，数据库只是由它派生的结果。这与 [keyword-terms.txt](../../retrieval/keyword-terms.txt) 放在 `retrieval/` 中的做法一致。这样做的理由：

- 新增或修改规格可以通过 git diff 审核。
- 评测的 D 类标注也读这个文件，见 8.1。
- 数据都来自公开评测，attributes.json 已有提交的先例。

格式是一个列表，每台机器一条记录，字段与 5.1 相同，外键改为用 `key` 表示：

```json
{
  "key": "联想 来酷GT 16 酷睿版",
  "brand": "联想",
  "price_cny": 5999, "price_kind": "reference", "price_date": "2026-09-28",
  "weight_kg": 2.23, "screen_inch": 16.0, "panel": "lcd",
  "has_dgpu": true, "gpu": "RTX 3050", "battery_hours": null, "is_gaming": true,
  "ports": {"usb_a": true, "usb_c": true, "video_out": true, "hdmi": true,
            "rj45": true, "card_reader": false, "thunderbolt": false, "oculink": false},
  "ports_text": "接口方面，机身左侧有两个USB-A 5Gbps……",
  "extra": {},
  "evidence": {"weight_kg": "重量 2.23kg"},
  "note": ""
}
```

（数值仅示意格式。）

`import_specs` 命令：

```sh
python manage.py import_specs --file products/specs/bibar.json --dry-run
```

- 先用 Serializer 校验字段类型、取值范围和枚举，再关联父段，然后按 `key` 新增或更新记录。
- `evidence` 中字符串形式的引用（来自评测原文），去掉空白后必须是对应评测父段正文的子串，用来发现外部 LLM 编造的内容；`{source, quote}` 形式的引用（联网补充）只检查 `source` 是 http(s) 链接、`quote` 非空，不抓取网页。
- 文件中已不存在的机型从库中删除，由试运行报告先列出来。
- 报告分为：新增、更新、未变、删除、失去关联、校验失败。
- 有校验失败时，整个文件都不写库。

### 5.4 评测子块记录小节名

推荐结果要附上评测结论，所以需要知道每个子块属于哪个小节。[ReviewStrategy._chunks](../../ingestion/strategies.py) 切分时已经维护了当前小节变量 `section`，但没有写进子块。改动如下：

- 子块元数据写入 `{"sections": [...]}`，即子块覆盖的一级栏目名，按出现顺序去重。过短的块会被合并，所以一个子块可能跨多个栏目。
- 以下栏目视为结论：总结、结论、优缺点、优点、缺点、购买建议、推荐理由、不推荐理由、猪王的良心结语。这个集合放在 `products/` 中，不改 `_REVIEW_SECTIONS`。
- 某篇评测没有结论栏目时，取该父段的最后一个子块。

影响：

- **schema 版本**：父段和子块的边界、key、检索文本都不变，只新增元数据，因此仍为 `product_review@1`。
- **重新编码**：元数据变化会改变内容哈希，78 篇评测都要重新导入，全部子块重新生成 Embedding，只需做一次。
- **排序结果应完全一致**：重新导入后用 `compare_runs.py` 与 v16 对比，结果应逐条相同。

## 6. 推荐接口

### 6.1 请求与条件

```json
{"conditions": {"price_max": 10000, "weight_max": 2.3, "is_gaming": true,
                "gpu_in": ["RTX 5060", "RTX 5070"]},
 "preference": "性能释放强、散热好",
 "top_k": 5}
```

`conditions` 只接受原子条件，用 StrictSerializer 校验，未知字段直接报错：

| 条件 | 含义 |
| --- | --- |
| `price_min`、`price_max` | 价格区间（元） |
| `weight_max` | 重量上限（kg） |
| `screen_min`、`screen_max` | 屏幕尺寸区间（英寸） |
| `battery_min` | 续航下限（小时，日常应用仿真） |
| `gpu_in` | 独显型号集合 |
| `has_dgpu`、`is_gaming` | 是否有独显、是否游戏本 |
| `panel` | 面板类型 |
| `ports` | 必须具备的接口列表 |
| `brands` | 品牌集合 |

- `conditions` 可以为空，表示只按 `preference` 在全部机型中排序。
- `preference` 可选，为空时按评测日期由新到旧排序。
- `top_k` 为 1～20，默认 5。
- 认证与可见范围与 `search/` 相同。

### 6.2 处理流程

1. **硬条件过滤**：按 `conditions` 查询有可见评测的机型。任何条件字段为空的机型都不满足该条件。
2. **统计未知**：对每个可能为空的条件字段，统计“其他条件都满足、只是该字段为空”的机型数，作为 `unknown` 返回。
3. **软条件排序**：把检索范围限定为候选机型的评测父段（`SearchScope` 新增 `context_ids`，在 [scoped_contexts](../../catalog/selectors.py) 中过滤），用 `preference` 跑现有召回和后处理流水线，取全部候选父段的名次。文本没有命中的候选排在后面，按评测日期由新到旧排列。
4. **组装结果**：取前 `top_k` 台。每台机器附上规格卡、结论子块（最多 3 个，按原文顺序）和软条件命中子块（最多 2 个，取该父段在第 3 步中的命中项）。
5. **结果为空**：`result_status = "no_result"`，在 `diagnostics` 中给出单独满足每个条件的机型数，供上层 LLM 判断放宽哪个条件。检索系统不自动放宽。

候选规模最多是全部评测机型（78 台），第 3 步的范围比现在的全库检索还小，不需要额外的性能处理。

### 6.3 响应

```json
{
  "result_status": "found",
  "products": [{
    "key": "…", "spec": {"price_cny": 0, "price_kind": "launch", "price_date": "…", "weight_kg": 0, "…": "…"},
    "review": {"context_id": "…", "title": "…",
               "source": {"title": "…", "url": "…", "source_date": "…"},
               "conclusions": [{"evidence_id": "…", "key": "…", "sections": ["优缺点"], "text": "…"}],
               "highlights": [{"evidence_id": "…", "key": "…", "sections": ["散热分析"], "text": "…", "score": 0.05}]}
  }],
  "unknown": {"battery_hours": 3},
  "diagnostics": null
}
```

需要整篇评测时，上层可以用 `context_id` 调用知识检索，或者由后续版本另提供读取接口。本方案不在推荐响应中返回评测全文，避免响应过大。接口契约要同步到[一期技术设计第 6 节](../phase1/phase1-technical-design.md#6-api-与错误)。

## 7. 规格填写

项目内不实现规格提取，也不调用任何对话模型。每导入一篇评测，由维护者按[维护手册 2.4 节的规格填写](../maintenance.md#规格填写)补一条规格记录：

1. 从库中导出这台机器的评测父段正文。
2. 人工填写，或把手册中的规则连同正文交给外部 LLM 生成草稿；原文缺失的字段可联网补充。
3. 人工逐字段核对引用，联网补充的要点开来源链接。
4. 合入规格文件，用 `import_specs` 试运行后导入。

手册用一张表说明每个字段的单位和口径（价格优先取参考价或首发价、续航只取日常应用仿真、显卡型号写法等），要求规格字段附上逐字复制的引用，并给出一条完整示例。原文缺失的字段可以联网补充并注明来源链接，续航除外。人工和外部 LLM 用同一份规则。

把关分两层：

- **人工核对**：重点是价格口径、续航、接口，以及联网补充的字段来源是否可靠、配置是否与评测机一致。
- **导入校验**：`import_specs` 检查字段合法性，以及来自评测原文的引用确实出现在评测正文中（5.3）。联网补充的字段只能靠人工核对。

使用外部 LLM 时，只发送公开的笔吧评测正文，不发送语雀内部文档。选用哪个模型由维护者决定。

## 8. 评测设计

### 8.1 标注来源调整

- D 类标注改为读取规格文件（P1 起）。之后新增评测时，只维护规格文件这一张表。[维护手册 2.4 节](../maintenance.md#24-公众号评测)第 4 步“补属性表”相应改为“补规格”。
- attributes.json 冻结，不再随语料更新，只作为试用外部 LLM 时比对填写效果的参照（[维护手册](../maintenance.md#规格填写)）。
- **自证问题**：D 类标注和推荐过滤用的是同一份规格数据，所以纯硬条件查询直接以标准条件调用推荐接口时，P@5 理论上必然为 1。P1 的这项结果只能说明“链路正确”，说明不了推荐质量；P3 衡量的是上层 LLM 换算条件带来的损失；规格数据本身的准确性靠人工核对和导入时的引用校验保证。

### 8.2 各阶段指标

| 阶段 | 指标 | 说明 |
| --- | --- | --- |
| P1 | 回归：170 条查询的知识检索结果与 v16 逐条相同 | 小节名重新导入后验证一次；`search/` 不改动，接口完成后再确认一次 |
| P1 | 链路：D 类标准条件由评测器换算成原子条件（换算规则在评测器内，沿用 [recall_eval.py](../../eval/recall_eval.py) 的 `CONSTRAINTS`）后调用推荐服务，纯硬条件查询 P@5 = 1 | 不为 1 说明过滤有错 |
| P1 | 软条件排序：新增 6～8 条“硬条件 + 软条件”查询（如“一万以内散热好的游戏本”“续航长、屏幕好的轻薄本”），按评测测试数据人工分级标注；比较“按 `preference` 排序”和“只按日期”两种排序的 nDCG@5 | 新类别字母待定（如 S）。D01、D04 一并纳入这一组 |
| P1 | 结论附带率：被推荐机型中附上了结论子块的比例 | 同时报告没有结论栏目、取最后子块兜底的篇数 |
| P3 | 工具选择：全部 170 条查询中选对工具的比例；D 类应选推荐，A～C、E、F、X 应选知识检索 | 衡量上层 LLM 按工具定义调用的效果 |
| P3 | 条件换算：D 类 19 条中，LLM 给出的原子条件与标准条件一致的条数，逐条列出差异 | 差异不一定是错误，例如“预算 8000”换算成 7000～9000 也合理，需要逐条判断 |
| P3 | 端到端：D 类 P@5、nDCG@5，与 P1 链路结果对比 | 差值即 LLM 理解问题带来的损失 |

P3 的评测脚本放在 `eval/`，用一个 LLM 加两个工具定义模拟上层系统。它只用于验证工具定义是否清楚、参考口径是否容易遵循，不进入线上链路。上层系统使用的模型不同，结果也会不同，正式效果以上层系统自己的评测为准。

## 10. 风险与待定事项

| 事项 | 影响 | 处理 |
| --- | --- | --- |
| 上层 LLM 换算口径不一致 | 相同说法在不同调用中得到不同区间，推荐结果不稳定 | 工具定义给出参考口径与示例；P3 评测统计差异；最终由上层系统的提示词约束 |
| 上层 LLM 选错工具 | 配置类问题被当作推荐，或推荐类问题走了知识检索 | P3 统计工具选择准确率；工具定义写清各自的适用场景 |
| 外部 LLM 编造或误读规格 | 推荐结果包含错误规格 | 填写规则要求逐字引用；导入时校验引用；人工核对价格、续航、接口 |
| 使用外部 LLM 时外发评测原文 | 原文发给第三方服务 | 只发送公开的笔吧评测，语雀内部文档不发送；选用哪个模型由维护者决定 |
| 价格过时 | 推荐了按当前价格已不符合预算的机型 | 返回值带 `price_kind`、`price_date`，由上层回答时注明是评测时的价格；不做价格更新 |
| 续航等字段缺失多 | 带续航条件时候选机型过少 | 返回 `unknown` 计数；不把缺失当作满足 |
| 主观条件（散热好、性能释放强）只能靠文本排序 | 排序质量有限 | P1.5 用软条件查询集衡量；必要时把噪音、双烤功耗等测试数据作为 `extra` 中的排序依据，再单独评估 |
| 修改 `entity_title` 导致失去关联 | 机型不再参与推荐 | 导入报告列出，改名后要同步修改规格文件的 `key` |
| 语料重复（MagicBook Pro 14 2025 的两版评测数据完全相同） | 推荐列表里出现两条几乎相同的结果 | 属于语料问题，不在本方案中处理 |
