首期指“资料抽样到知识服务可试用”的完整交付，不仅是资料准备阶段。需求编号沿用总需求；技术依据沿用 2026-09-27 的调研，不代表已经部署或通过实测。默认假设至少有一名 Python 维护者，服务器、模型资源与预算在实施前确认。

本文确定首期范围与选型；数据对象、API 字段和各迭代运行行为统一详见[首期技术设计](/home/kurfuerst/Coding/nju/itxiaRAG/docs/phase1/phase1-technical-design.md)。首期只服务每个来源的当前已放行构建，不实现来源历史查询或回滚；Schema、处理器和检索配置的版本仅用于重试、评估和重建。实现时由 DRF Serializer 校验并生成 OpenAPI，示例和客户端以同一契约对接；通用测试要求见[项目单元测试规范](/home/kurfuerst/Coding/nju/itxiaRAG/docs/unit-testing-guidelines.md)。

## 1. 首期目标与边界

首期交付一个由社团成员可以维护的知识服务，为 itxiaAgent 提供经过权限筛选、带来源定位的证据。平台首期保留语雀笔记、维修经验记录和笔吧评测等三类来源的统一接入、版本、权限和查询契约；父子分块的第一个具体处理策略先以笔吧笔记本评测验证。语雀基础知识、维修记录和其他文章类型按各自 Schema／处理器接入，不被笔吧规则限制。

首期采用人工准备输入、自动质量校验和异常复核，先用 TXT／Markdown 与代表性样本打通三类来源的通用链路；笔吧评测使用已定义的“一台对象一个父上下文”处理策略。Agent 可先整理查询与已确认条件，也可直接提交原始查询；知识库负责版本、权限、证据和检索，并保留可替换的查询预处理模块。首期预处理透传，意图识别、查询改写及条件提取后续按需接入；对话状态、追问和最终回答仍由外部应用负责。

“首个处理版本”不等于“完整首期交付”：可以先单独运行笔吧评测链路，再补齐其他来源的处理器与验收；完整首期仍以本文三类来源、三个场景的验收目标为准。

本次实现范围包括维护命令／维护 API、导入 Worker 和数据存储；Django Admin 作为可选维护界面，不是首期交付前置。M7 只定义知识库对外接口，Agent 开发、追问与最终回答生成及转人工交互均由外部应用负责。首期不接入生成模型，后续用于查询理解的模型由 M5 查询预处理子模块按需适配。常识、购机和维修查询均保留接口与验收契约；具体资料覆盖随对应来源样本和处理器落地，不要求用笔吧评测冒充维修依据。首期可使用 API 测试客户端完成，无需开发 Agent。

### 1.1 首期必须支持

- **来源与构建**：通过管理命令／API 提交 TXT、Markdown 和来源参数；记录来源、日期、授权、构建、导入状态和撤回状态。其他格式先由成员整理为这两种输入，原始链接和必要表格随附。
- **知识整理**：统一保存可独立引用的父上下文和负责检索的子块。首个 `product_review.v1` 策略按“一篇文章中的一台笔记本一个父段”保存完整评测，父段内按测试／配置／评价切检索子块；其他 Schema 按自身完整语义边界生成父段。专门的 FAQ／主题页／Spec 编辑模块后续实现。
- **混合检索**：`query` 同时接受原始问题和已整理文本，支持自然语言和关键词，并结合已确认的型号、年份、错误码和配置字段检索。
- **查询预处理扩展点**：M5 内定义统一输入输出、处理器接口、透传实现和失败回退；首期不做意图识别／智能改写，后续可接入规则或 LLM，已处理请求可显式跳过。
- **检索返回**：返回完整父上下文 contexts[]、命中子块标识、完整父段的子块引用、来源定位、构建标识、日期和条件；top_k 计父段数量；支持无结果、条件不足、已标注冲突和过期资料状态，不生成回答。
- **权限与发布**：普通用户只能获得公开且已通过质量放行的知识；社员可按授权访问内部知识；停用或撤回的内容不能进入默认检索结果。正常任务自动放行，异常或新处理器样本需要维护者复核；硬错误不能强制发布。
- **反馈与评估**：迭代四补齐 QueryRecord 与反馈关联；此前可独立查询并返回查询标识，但不开放反馈。维护代表性问题集，比较检索结果与接口行为，并保存必要的结构化 Trace。
- **备份与恢复**：导入失败不影响已发布版本，数据库、原始文件和配置可以恢复。

### 1.2 首期不承诺

首期暂不实现 M6 知识页／Spec／派生证据整理模块，也不包含 Agent 开发、生成模型接入、自动连接语雀或公众号的同步接口、实时信息查询、自动生成并发布知识、独立图数据库、全库 GraphRAG、自动微调、持续自进化闭环和复杂多租户。复杂 PDF 或扫描图片只有在样本证明需要时才引入解析扩展。

## 2. 首期用户、场景与数据

### 2.1 用户角色

| 角色 | 首期能力 | 数据范围 |
| --- | --- | --- |
| 普通师生、新生 | 电脑常识、购机参考、低风险故障自查 | 已通过质量放行的公开知识 |
| 社员 | 常识、购机和维修查询，以及获授权内部参考 | 公开知识及获授权的内部知识 |
| 知识维护者 | 导入、整理、处理异常复核、停用、修订、查看反馈和评估 | 管理权限范围内的来源和知识 |

权限需在检索、引用、日志和原文查看环节一致执行。

首期知识访问范围只使用 `visibility=public/internal` 区分：普通用户只读取 `public`，已认证社员可读取 `public` 和 `internal`。不设置来源级细分权限；社员身份由服务端认证映射，客户端不能自行声明。

### 2.2 首期来源与保留字段

| 来源 | 首期接入方式 | 至少保留 |
| --- | --- | --- |
| 社团语雀笔记 | 首期可提交获准 TXT／Markdown；后续接入授权读取 | 标题层级、原始标识或地址、作者／维护者、原始更新时间（未知可为空）、公开／内部属性 |
| 维修经验记录 | 首期可人工导入脱敏文本，并按维修 Schema 校验 | 记录时间、设备与系统、症状、已做检查、措施、结果、未确认项和风险 |
| 笔吧笔记本评测推文 | 首期可提交获准 TXT／Markdown，并先验收 `product_review.v1` | 标题、作者／账号、原始地址、发布日期、机型和具体配置、测试条件、价格日期与条件 |

不能保存全文时，只保存允许的摘录、结构化事实、元数据和原文链接。原始内容的发布日期与系统导入日期分开记录；无法取得原始日期时标记为未知。

### 2.3 知识类型与当前覆盖

| 类型 | 首期结果 | 必须保留的约束 |
| --- | --- | --- |
| 概念／FAQ | 来源中的概念和问答片段，可被检索返回 | 解释范围、软件版本依赖和来源；专门 FAQ 页面后续实现 |
| 产品／配置 | 可用于筛选和比较的结构化字段 | 具体型号、年份、CPU/GPU、内存、存储等；系列名不能替代配置 |
| 购机结论／价格 | 带日期和条件的参考 | 区分规格、评测体验、主观推荐和历史价格 |
| 维修案例 | 供相似案例查询的记录 | 观察事实、推测、已确认结论、措施、结果和适用差异分开 |
| 排查流程记录 | 来源中的步骤、警告和结果分支 | 前提、步骤、停止／转人工条件和来源；专门 Spec 编辑后续实现 |

## 3. 首期功能需求

下表沿用总体需求编号；通用平台和三类来源的接口、权限、发布与失败边界属于首期范围。父子分块专项先用笔吧评测样本验收；语雀和维修的领域字段与处理规则在对应处理器启用时补充专项样本，不能用评测样本代替维修依据。

| 编号 | 首期需求 | 首期验收条件 | 对应模块 |
| --- | --- | --- | --- |
| F-01 | 导入授权的语雀、维修记录和笔吧评测及来源信息 | 三类来源各有至少一份可追溯样本；自动校验的成功、失败、待复核和缺失字段可见，标题、正文和来源定位保留 | M1、M2、M3、M4 |
| F-02 | 整理文档结构并保留上下文 | 按 Schema 确定父段边界；笔吧首个策略一台一个父段、多台多个父段；子块与完整父段均可定位 | M2、M3 |
| F-03 | 识别重复导入和内容更新 | 同一来源、同一内容和索引配置不产生重复有效候选；新构建完成索引并通过自动／人工放行后切换 current_build_id，失败或待复核保留当前构建，旧引用返回 404 | M2、M4 |
| F-04 | 整理产品、概念、案例、流程并统一别名 | 常见俗称可检索；不同年份、配置和设备保持区分；不确定的关联进入待确认状态 | M1、M2、M3、M5 |
| F-05 | 来源质量放行、停用、修订和撤回 | 未放行候选不公开；正常任务自动放行，异常由维护者复核；停用／撤回内容不进入默认检索，维护者能看到操作记录 | M1、M2 |
| F-07 | 支持原始／已整理查询、关键词、型号和错误码，保留预处理扩展点 | 保留关键检索对象；透传与主动跳过均可独立查询，处理器可替换，首期无需生成模型 | M3、M5 |
| F-08 | 按权限、状态、设备、版本和时间筛选证据 | 调用者不能命中无权内容；明显不匹配的型号／版本不作为直接依据；条件不足时返回缺失条件 | M1、M2、M5、M7 |
| F-09 | 返回结构化检索结果 | contexts[] 含完整父上下文及出处，matched_evidence_ids／citations 标识子块；不混用父子 ID | M5、M7 |
| F-10 | 保留检索结果的来源追溯信息 | 片段 ID 可定位到授权范围内的来源、当前构建和原文位置，调用方能核查原文；不实现回答断言与证据的自动核验 | M2、M5、M7 |
| F-12 | 为常识问答提供可用证据 | 对已收录问题返回易懂解释所需的证据、出处和适用范围；缺少证据时明确说明 | M5、M7 |
| F-13 | 为基本购机匹配和比较提供证据 | 返回预算、用途、便携等条件对应的配置、取舍、适用人群和资料日期；条件不足时返回缺失条件 | M3、M5、M7 |
| F-14 | 为低风险故障自查和社员参考提供证据 | 返回下一步检查、目的、结果分支、停止条件和案例差异；不把相似案例当作确诊 | M3、M5、M7 |
| F-15 | 返回信息不足和转人工所需信息 | 不补造配置、价格或诊断；资料缺失与用户条件未知分开，已有停止操作和转人工证据完整返回 | M5、M7 |
| F-18 | 接收并定位反馈 | 错误、过时和无帮助反馈能关联原查询、证据、来源和构建；反馈不会自动成为知识 | M1、M2、M7、M8 |
| F-20 | 维护问题集并比较版本 | 记录问题、预期来源、检索结果、人工相关性评审和配置版本，定位漏召回、错误来源和退化 | M8 |

### 3.1 首期返回内容的边界

购机结果保留具体配置、测试条件和价格日期，资料过旧或条件缺失时返回相应状态。维修结果须保留来源中的检查步骤、风险、前提、停止条件和原因是否确认，不将检索相似度解释为故障确诊。追问、最终推荐和转人工提示由调用方负责。内部资料要服务公开查询，须先形成获准的脱敏公开来源，不能仅隐藏链接。

## 4. 首期技术模块与选型

### 4.1 模块总表

| 编号 | 模块 | 首期默认技术与选择理由 | 首期实现范围 | 主要替代与首期不选原因 |
| --- | --- | --- | --- | --- |
| M1 | Web、维护入口与 API | Django 5.2 LTS + DRF：复用 ORM、迁移、认证与 API；管理命令为首期维护入口，Django Admin 可按需启用 | 维护命令／API 提交来源、查看任务、处理异常、发布／停用和反馈；不要求首期自定义网页后台，所有入口共用业务规则 | FastAPI 也能提供 API／命令，但需组合 ORM、迁移和认证；当前采用 Django 可复用这些基础能力 |
| M2 | 来源、当前构建与知识存储 | PostgreSQL：同库维护来源、构建、片段和状态；附件按需使用私有文件卷 | 来源、导入任务、父段、子块、配置、别名、审核、权限和反馈；不预建知识页或 Spec 子系统 | MongoDB 同样可用，但需额外设计跨对象一致性；独立向量库不能替代业务数据层；S3 服务非必需 |
| M3 | 文本解析、清洗与分块 | Python 格式解析器 + 按 document_schema 选择的可替换文档处理器 + tokenizer：保留语义边界并控制长度 | 格式解析保留标题／列表／表格；类型处理器按各自 Schema 生成父段，再切检索子块；首个评测策略以每台笔记本为父段，输出 ProcessedDocument 和定位；脱敏与字段填写由规则辅助、成员确认 | 固定窗口容易拆散警告和配置；Docling／OCR 留待复杂格式确有需求时引入 |
| M4 | 管线与任务执行 | Python 模块化导入流程 + PostgreSQL 任务表 + 单 Worker：首期少依赖，步骤和接口由项目明确约定 | 按固定配置调用 M3，统一校验、embedding、索引、幂等写入和有限重试；记录步骤状态、耗时和错误。各类型复用一个 Worker，构建成功后调用 M2 自动放行或转人工复核 | Haystack 可作为后续可选编排框架；Celery 适合更复杂调度但增加 broker；不把框架引入作为首期前提 |
| M5 | 查询预处理、召回与过滤 | Python 处理器接口 + 默认透传；Qwen3-Embedding-0.6B + pgvector + PGroonga + RRF | 预处理可替换／跳过；SQL 权限／字段条件、两路召回、融合、去重、子块候选复核、父段聚合和返回预算；精确向量检索起步 | 首期不引入通用插件框架或改写模型；规则／LLM 处理器列 P1。仅向量易混淆配置；仅词法难覆盖口语 |
| M6 | 知识页、Spec 与派生证据整理（P1 暂缓） | 首期暂不实现；后续再选 Markdown、Schema 和依赖管理方案 | 后续提供 FAQ／主题页／Spec 编辑、审核、派生证据及其来源依赖管理；首期不建立这一子系统 | 首期片段自身的来源、版本、位置归 M2/M5/M7，不等于实现本模块 |
| M7 | 知识库对外接口 | DRF 实现的版本化知识查询与维护 API：让 itxiaAgent 或其他客户端调用知识库，不包含 Agent 实现 | 查询输入、权限上下文、证据列表、缺失条件、冲突／过期状态、引用查看、反馈和维护接口；服务端确认调用身份 | 不开发 Agent 或直接适配模型；聊天入口与最终回答生成由外部应用负责，可选查询理解模型封装在 M5 |
| M8 | 评估、观测与运行 | 离线检索指标 + 人工相关性评审 + 结构化日志 + Docker Compose | 检索评估、请求关联、耗时、错误、备份恢复和操作说明；不以回答生成评估作为首期交付门槛 | Ragas 等工具可后续按指标复用；首期不为 LLM judge 接入生成模型，Langfuse 等平台也不强制部署 |

### 4.2 默认配置与实测候选

“首期需求必须满足”不等于“候选技术必须全部启用”。上线使用一套经评估的配置；以下区分默认项、对照项和条件项。

| 对象 | 默认或候选 | 选择理由与决定方式 |
| --- | --- | --- |
| Embedding | 默认 Qwen3-Embedding-0.6B，1024 维 | 多语言、可用查询任务指令、尺寸较小，适合先验证；不据此承诺 CPU 或 GPU 延迟。查询与文档编码按模型卡约定执行 |
| Embedding 对照 | BGE-M3，仅 dense 模式 | 同样可输出 1024 维，使用 dense 不需要三套索引；用同一问题集比较，若更适合社团语料则替换 Qwen |
| 词法检索 | 默认 PGroonga | PostgreSQL 内提供中文全文检索；先验证扩展兼容性。无法部署时用应用预分词（如 jieba）+ PostgreSQL FTS 作回退，不退化为仅向量 |
| 向量索引 | 默认精确检索；HNSW 为条件项 | 先建立准确性与耗时基线，仅在数据量／延迟实测需要时启用近似索引，再检查过滤后的召回 |
| 融合 | 默认 RRF | 按排名融合，不要求词法和向量分数同尺度；PGroonga 词法分数不直接称作 BM25 |
| 重排 | 无重排为基线；Qwen3-Reranker-0.6B 为对照项 | 比较命中率、MRR、相关性与增加的延迟／费用；收益不足时关闭，首期不同时部署多个 reranker |
| 数据库／依赖版本 | 部署前锁定兼容版本 | PostgreSQL、两个扩展、Python 包和模型权重需记录版本。文档编码模型、维度或模板变化须重建；兼容的查询编码指令及在线策略调整独立评估、切换 |

组件官方资料与对照依据见[技术选型总文档第 3、4、7 节](/home/kurfuerst/Coding/nju/itxiaRAG/docs/technology-selection.md)。首期默认由成员整理字段、别名和来源中的问答／流程片段；M6 的专门 FAQ／主题页／Spec 编辑和模型草稿不作为首期依赖。

### 4.3 最小运行架构

```text
维护者 → 管理命令／DRF API（Admin 可选）→ PostgreSQL（来源、当前构建、权限、证据、任务、反馈）
                         → 私有文件卷（可选附件，使用时备份）

单个导入 Worker + Python 模块 ← PostgreSQL 任务表／可选文件输入
  格式解析 → 按 Schema 生成父段／子块 → 统一校验 → Embedding／索引与写入
                                                     → 质量检查 → 自动发布或维护者异常复核

外部客户端（可为 itxiaAgent 或 API 测试客户端）→ 查询 API → 预处理（首期透传）→ 权限与状态过滤
             → PGroonga + pgvector → RRF →（可选）Reranker
             → 父段 + 子块引用 + 来源／构建／位置 + 状态 → 返回客户端
```

完整首期需要 Web/API、单个 Worker 和 PostgreSQL 三个运行单元；早期迭代按第 6 节启用依赖。Python 导入模块在 Worker 进程内，PGroonga 和 pgvector 是 PostgreSQL 扩展，检索评估离线运行。Redis、MinIO、独立向量库、图数据库、Haystack 和 Langfuse 不属于默认首期部署。

Embedding 及可选 reranker 仍需可用的本地推理或获准服务；它们服务于检索，不包含回答生成模型。M1 负责框架、认证、API 与管理命令，Admin 按需启用；M7 定义同一 DRF 服务的对外契约，两者不是两套服务。

### 4.4 关键技术决定

#### 检索默认方案

1. **权限过滤约束所有召回与返回。** SQL 条件和应用权限决定可见范围；近似向量检索只影响候选数量，不能当作访问控制。候选在进入重排或返回前复核状态。
2. **RRF 作为融合起点。** PGroonga 和 pgvector 分数不保证同尺度，首期不凭经验混加分数；有标注数据后再比较加权融合。
3. **精确向量检索先行。** 先用 exact baseline 取得质量和延迟数据；HNSW 可能在高选择性过滤时返回不足，是否启用由试测决定。
4. **重排可开关。** 比较 Qwen3-Reranker-0.6B 启闭时的检索命中率、MRR、相关性、P95 和成本，没有稳定收益就关闭。

型号、系统等条件仅在信息明确时参与匹配，未知值保留未知；不能因用户未提供型号而丢弃适用的通用知识，也不能把配置未知的材料当作精确匹配。预算与用途的关键条件不足时由 Agent 追问。

#### 来源维护与 M6 的边界

M1/M2 首期支持来源文本与元数据维护、自动质量放行、异常复核和停用。任务构建成功且符合已验证配置时自动放行并切换 current_build_id；带复核标记的任务由维护者处理后再发布。停用和撤回由来源状态单独控制。正文和内容元数据修订创建新任务，不能直接修改在线父子产物；已知错误或高风险失效立即停用。

首期通过命令／API 完成维护，Markdown／HTML 质量报告供样本验收与抽查，DBeaver／pgAdmin 只读查看来源、任务与父子表。正式写入统一经业务服务，不手工改 current_build_id 或在线正文。自动放行配置须记录已验证的 Schema／处理器版本；未放行候选不能查询，已发布内容的时效“待复查”标记与此区分。具体规则见技术设计第 3.2～3.4、4.3 节。

M6 后续才建设独立知识页、Spec 字段／分支解释、派生证据和依赖管理。已有 FAQ 或流程文档可以作为普通来源导入，不需要为此提前实现 M6。首期只维护来源、导入任务到父子片段及索引的关联，不创建派生页面子系统。

#### 任务可靠性与发布切换

`import_job` 同时保存本次固定输入、content_hash、IndexProfile、任务状态、放行记录和质量报告，id 即 build_id；不另建来源版本表。单 Worker 按格式和 Schema 解析、生成父子产物并建立索引，重试使用原任务输入和配置。构建成功且自动／人工放行后，检查来源权限、配置和 base_build_id 未过时，再原子切换 knowledge_source.current_build_id；失败不影响当前构建。更新与重建均重新取得最新获准内容或人工上传，创建新任务并按策略自动放行或转人工复核；首期自动采集仍为后续能力。撤回和限权立即阻断访问。被替换构建可清理，旧引用返回 404，不提供历史正文查询或回滚。

#### 配置分层与可替换组件

`IndexProfile` 固定文档解析、分块和索引配置，`QueryProfile` 管理兼容的查询策略；只调 RRF／重排／预处理不重建文档。模型或索引升级允许停机：暂停查询与发布，建立并验证候选，整体切换后恢复服务；普通内容更新仍原子替换、失败保旧。

解析器、内容处理器、编码器、词法后端、重排和查询预处理用少量函数／Protocol 隔离，复用一个 Worker，不引入通用插件框架。字段、hash、兼容性和切换规则统一见[技术设计](./phase1-technical-design.md)第 2.5、2.6、4.4 节。

#### 知识库对外接口的最小约定

| 交互 | 首期承载的信息 |
| --- | --- |
| 查询输入 | 原始或已整理文本 `query`、可选 `preprocess=auto/bypass`、场景 `scenario`、已确认条件 `confirmed_context`、`filters` 与 `top_k`；调用身份由服务端认证映射 |
| 检索输出 | UUID query_id、两类配置 hash、feedback_available、预处理摘要、证据列表、缺失条件、冲突／过旧／不足状态；contexts[] 单项含 context_id、完整 text、scope_fields、字段出处、子块引用及来源状态；top_k 按父段计 |
| 引用查看 | 按证据 ID 获取当前允许查看的出处；再次检查授权和撤回状态 |
| 维护接口 | 获授权的维护者可以提交来源、更新元数据、查看导入状态、处理待复核任务、停用、修订和撤回；与管理命令及可选 Admin 共用业务规则 |
| 反馈关联 | 迭代四起关联当前调用者仍在保存期限内的 QueryRecord 及实际返回的证据；无结果也可反馈；首期不要求报送或保存生成的回答 |

首期预处理透传，支持原始／已整理 query 与 auto／bypass。后续规则／LLM 不覆盖显式场景和已确认条件，提取条件只作建议，失败回退原查询；客户端负责追问及生成回答。请求校验、缺失条件和响应字段统一见技术设计第 2.4、6 节。

所有阶段生成 query_id。迭代一至三返回 `feedback_available=false`；迭代四成功保存 QueryRecord 后为 true，写入失败仍返回已完成的检索结果、置为 false 并记录故障。反馈只接受本人仍有效的记录，不用客户端数据补认不存在的查询。

### 5.1 首期目标值与试测条件

沿用需求文档中的建议目标，以下都是待验证目标，不是现有成绩：

- 前 5 个父上下文中包含有效依据的检索命中率：≥ 90%。
- 证据追溯专项：返回的当前证据 ID、来源、构建和原文位置可核查，验收用例全部通过。
- 时效、产品归属、局部条件完整性、维修风险和隐私专项：验收用例全部通过。
- 检索 P95：目标 ≤ 2 秒，包含在线 embedding 和启用的重排。
- 建议先用约 1000 篇文本、5 个并发查询试测，同时记录总字符量、父段数、子块数、token 数和硬件条件。

父段 Hit@5／Recall@5／MRR 与旧子块指标分开，增加产品归属正确率、条件完整率及无关内容比例。无答案问题单独统计；前 5 命中一项依据不等于多证据问题的全部依据都已召回，还需人工检查关键依据是否齐全。通过有限专项用例不等于证明不存在其他问题。总体需求保留的回答可接受率、回答引用支持率和完整回答延迟，在外部 Agent 接入后另行验证，不属于本期交付门槛。

性能报告需将 query embedding、数据库召回、重排和排队分别计时。若使用外部检索模型服务，记录调用费用和数据处理范围；若本地部署，记录显存、量化、批大小和并发。不能把“文章篇数”直接当作容量指标。质量口径、性能目标和预算上限在样本试测后确认，未达到时报告差距与调整决定。

## 6. 首期实施顺序

样本、授权、维护负责人和问题集准备贯穿首个迭代：三类来源各选取少量获准样本；其中笔吧评测覆盖单机、多机、配置差异和表格，维修样本覆盖症状、检查和风险，语雀样本覆盖标题层级和基础知识。准备至少 60 个跨场景问题（常识／购机／维修各不少于 15 题）并划分开发／独立验收集；确认访问范围、保存期限及实际部署资源。样本准备不单独算一个可运行软件版本。

首期软件按技术设计第 8 节的四个迭代交付；各版本均须能从空库启动、执行真实维护与查询操作，不依赖后续能力。迭代一的模块、接口及验收清单见[迭代一实现文档](./phase1-iteration1-implementation.md)，当前范围为 manual 短笔记同步构建与关键词查询，暂不包含笔吧推文导入与导入／解析 Worker。

迭代一进一步收敛：domain_metadata 只接受省略或 `{}`，子块知识类型固定 concept，冲突标注与领域投影后续实现；保留 Markdown 有意义的行尾空格。同步导入返回 200 和实际任务结果，迭代二引入 Worker 后异步接收新任务才返回 202，状态码细则以技术设计第 6.1 节为准。

| 迭代 | 独立可用能力与依赖 | 验收重点 |
| --- | --- | --- |
| 一：维护与关键词查询 | API／管理命令 + PostgreSQL；4 张核心表和 retrieval_settings，共 5 张业务表；无需 Worker／模型或附件卷 | manual + generic_note.v1 自编／合成短笔记同步生成一父一子，经自动检查／异常复核后查询、引用和撤回；暂不包含笔吧导入；支持 general 无条件关键词查询、字段校验、透传／跳过、visibility 权限；query_id 与两类配置 hash 可查，反馈尚未开放 |
| 二：文件导入与词法检索 | 增加单 Worker、TXT／Markdown 解析和 PGroonga 或已验证 FTS；仍为 5 张业务表 | 正式实现并验收笔吧 `product_review.v1`：一台一父、多台分离并保留局部条件；语雀／维修处理器按已注册 Schema 接入；新处理器先样本复核，同配置正常任务自动放行；去重、内容更新、失败恢复；无需 embedding 即可查询 |
| 三：混合召回 | 增加 pgvector、真实 embedding、RRF 和场景条件规则；仍不依赖 QueryRecord／反馈 | 口语与精确字段查询、缺失条件／时效／冲突、模型降级；验证查询调参与索引维护升级的区别 |
| 四：评估与试用发布 | 增加 query_record、feedback，首期共 7 张业务表；反馈、评估、恢复与交接完整 | Qwen／BGE 与重排消融、固定配置和独立验收集；A-01～A-14 和各 Schema 父子专项、性能／成本、备份恢复与交接 |

表数量不包含 Django 框架表。开发采用一条主线与累积迁移，阶段固定镜像／版本；每个阶段分别验收空库启动和从上一阶段升级，不能通过手工跳过迁移伪造阶段配置。QueryRecord 只在迭代四提供反馈关联，不是查询结果返回的前提。

开发与合并遵守项目单元测试规范：验证字段、规则、处理器替换和失败回退；事务、权限过滤、构建幂等及配置切换另用 PostgreSQL 集成测试。发布时执行实际 API／Worker 与真实模型验收，不能用单测通过代替检索质量或独立运行验收。笔吧父段规则专项通过后，再按各自 Schema 的样本补齐语雀和维修领域验收。

| F-17 / M6 知识页、FAQ、Spec 与派生证据整理 | P1 | 来源检索可用后，确有跨来源整理和规范维护需求；首期暂不实现 |
| F-19 模型辅助 FAQ／案例／Spec 草稿 | P1 | 人工整理重复度高，且有来源、缺失字段和审核流程 |
| F-11 关联查询、LightRAG 或 query-local 图 | P1 | 多跳问题在问题集占比上升，关系表查询不足 |
| F-16 学习和科普素材整理功能 | P1 | 基础知识集可用后，再建设专门的主题材料汇总功能 |
| Celery、Redis、S3／MinIO、Langfuse | P1 | 并发、共享存储、任务调度或观测需求已被试测证实 |
| Haystack 编排框架 | 后续可选 | Python 模块的组合、分支和复用成本增加时再评估 |
| F-21～F-25 受控自进化 | P2 | 有持续反馈、独立回归集、审核人和成本上限；候选必须可回滚 |
| 微调／蒸馏 | P2 | 有足量高质量脱敏样本，且 RAG 与提示优化收益不足 |

首期保留机型—配置、案例—证据、片段—构建—来源等必要关系，使用 PostgreSQL 外键／关联表即可；不建设多跳图检索。来源修订属于前期能力，反馈处理在首期最终迭代启用；独立主题页、Spec、派生页面依赖管理及模型辅助草稿属于后续阶段。Agent 开发和最终回答生成由外部应用规划；知识库查询理解模型可在 P1 按需接入。
