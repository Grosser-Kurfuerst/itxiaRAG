# itxiaAgent 项目单元测试规范

版本：v0.4（同步自动质量放行与异常复核规则）  
日期：2026-09-30  
适用范围：项目全部 Python 业务模块、查询／导入编排、校验器和适配器。具体业务契约见[首期技术设计](/home/kurfuerst/Coding/nju/itxiaRAG/docs/phase1/phase1-technical-design.md)。

本文规定后续实现应遵守的测试规则与功能开发完成定义。当前仓库只有设计文档，以下目录、命令和 CI 检查均为待交付约定，不代表已有测试代码或测试已通过。

## 1. 目标与边界

单元测试用于证明一段业务行为在给定输入与依赖结果下符合契约，并使重构后仍能验证该行为。测试按可观察行为组织，不要求每个函数都有对应测试，也不为了覆盖率复制实现逻辑。

| 类别 | 验证什么 | 依赖边界 |
| --- | --- | --- |
| 单元测试 | 校验、转换、状态决策、排序规则、重试／回退编排 | 不访问真实数据库、网络、模型服务；允许临时目录和小型文本样本 |
| 离线契约测试 | 多个实现是否遵守同一协议；SDK／HTTP 响应映射是否正确 | 使用确定性 fake／stub 或模拟 HTTP transport；不调用真实供应商 |
| 集成测试 | ORM、事务、唯一约束、数据库检索、API 认证和持久化、真实文件边界 | 使用隔离 PostgreSQL 及必要扩展；按需使用本地测试服务 |
| 端到端／质量评估 | 导入到发布查询的完整路径、升级恢复、真实检索质量与性能 | 运行实际 API、Worker、真实检索模型和固定数据集 |

不能用 mock ORM 的测试证明事务、锁或唯一约束正确；不能用随机／固定假向量证明真实召回质量；不能用 SQLite 的结果代替 PostgreSQL 扩展验证。每份验证报告明确属于哪一层。

## 2. 工具与组织

默认使用 pytest；Django／数据库测试按需使用 pytest-django；pytest-cov 用于观察覆盖缺口。首个实现版本应固定开发依赖，并创建以下组织结构：

```text
tests/
  unit/          # 按 catalog、ingestion、retrieval、api 等模块组织
  contract/      # 不依赖外部服务的共享协议测试
  integration/   # PostgreSQL、API、适配器真实后端
  e2e/           # 发布版本的实际链路
  fixtures/      # 小型、合成或已授权脱敏样本
```

注册 `unit`、`contract`、`integration`、`e2e` 标记并启用严格标记检查，便于选择运行范围。同一测试的分类与目录保持一致。模型质量评估数据与一般 fixture 分开，不能把独立验收集的预期答案用于反复调整实现。

接口示例必须经过真实 Serializer 校验，并与生成的 OpenAPI 检查一致；自定义的未知字段、严格类型和跨字段规则也要有行为断言，不能仅检查 Schema 文件能被解析。校验器不需要数据库时归单元／离线契约测试；需要认证、ORM 或完整 API 路由时归集成测试。

纯单测无需创建数据库，不得用 autouse fixture 为整个测试套件自动启用数据库或启动模型。模块导入时也不得执行网络请求、迁移或下载权重。

## 3. 什么时候写测试

- 新增或改变业务规则、外部契约、状态转换、权限决策、错误分支时，增加或调整相关测试。
- 修复可稳定复现的业务错误时，先用最小回归用例暴露该错误；能先在旧实现上确认失败时，应执行一次确认。
- 纯格式、文字、无行为变化的简单重命名，不为凑数量新增单测；运行受影响的现有检查即可。
- 每项行为优先覆盖正常路径，以及与该契约直接相关的无效输入、缺失信息或依赖失败。不要穷举没有业务价值的极端组合。
- 业务契约变化时同步修改测试；只有实现重构时，原有行为测试通常应继续通过。

## 4. 用例写法与断言

1. 一个用例表达一个主要行为，按 Arrange／Act／Assert 组织，名称说明条件和结果，例如 `test_unknown_checks_are_reported_missing`。
2. 对同一规则的等价输入使用参数化；参数应有可读 ID，失败时能看出是哪种业务情况。
3. 断言业务输出、状态、字段路径和必要副作用。仅断言“没有抛异常”“返回非空”不足以验证契约。
4. 预期值来自需求或手工推导，不调用被测函数的辅助实现生成预期值，不复制生产算法作为测试 oracle。
5. 除协议明确要求外，不断言私有方法调用顺序、内部变量或固定 SQL 文本。重构不应无故破坏测试。
6. 精确断言稳定错误码与字段路径；不依赖易变化的中文提示全文、堆栈或日志排版。
7. 对 RRF、向量数值等使用明确的容差比较；不能用“差不多”掩盖模型身份、维度和条数错误。
8. 不滥用整份响应快照。UUID、时间和 hash 示例应按格式／关系断言；只有稳定格式本身是契约时才使用小型 snapshot，并人工审核变化。

## 5. Fixture、隔离和可复现性

- 使用最小样本：一份有效来源、一个不可见来源、一个失败响应即可说明的行为，不加载全量语料。
- 默认使用函数作用域 fixture；共享只读样本可以扩大作用域，不能让测试共享可变状态或依赖执行顺序。
- 时间、随机数、UUID 生成和重试等待通过依赖注入或固定来源控制。重试测试不执行真实 sleep，超时测试让 fake 返回超时结果。
- 文件测试使用 pytest 临时目录；结束后自动清理，不读取用户主目录、真实语雀笔记、线上数据库或生产 Token。
- 修改环境变量或配置时自动恢复；禁用向外部服务发送真实请求。测试通过不应依赖网络、密钥或 GPU。
- 失败必须可重复定位，不能用自动重跑把偶发失败变成通过。确需临时 xfail／skip 时说明原因和跟踪项，不把缺少核心依赖算成验收成功。

## 6. Test double 与适配器契约

优先在正式扩展边界注入小型 fake／stub，而不是 patch 多层内部方法。fake 必须遵守真实协议的输入输出和失败类型；默认不会自动为缺失字段补出“成功结果”。

| 边界 | 离线测试应覆盖 | 仍需集成验证 |
| --- | --- | --- |
| 查询预处理 | noop／bypass 保留输入；改写结果进入召回；超时／非法输出回退；显式条件不被覆盖 | 实际模型结构化输出、延迟和改写质量 |
| 解析与分块 | 标题／表格／步骤定位，必要前提和警告保留；空解析和格式错误 | 真实资料抽样、实际文件导入与持久化 |
| Embedding 适配 | 文档与查询模板区分；批次顺序和条数；维度不符、非有限数、限流与超时映射 | 真实模型向量空间、供应商兼容性及检索质量 |
| 词法后端 | 候选 ID／rank 映射，SearchScope 传递，异常不伪装成空结果 | PGroonga／FTS 实际应用权限、版本过滤与中文检索 |
| 重排适配 | 只返回输入候选 ID；缺失／重复 ID、非法分数导致整批回退 | 实际重排模型质量与资源消耗 |

同一协议的实现复用一组输入与行为断言，通过 fixture／参数化选择适配器；新增实现先通过共享契约测试，再做对应的真实后端验证。mock 供应商响应应驱动实际适配代码，不能 mock 掉被测适配器本身。尚未接入的 P1 模型只用 fake 验证扩展边界，不为其预建调用服务或大量实现细节测试。

依赖调用是否发生只有在它本身属于契约时才断言，例如 bypass 不调用 LLM、未通过质量放行不发布、已失败的配置不进入向量检索。不要用“某个 helper 调用了几次”代替业务结果。

## 7. 项目重点行为清单

此表用于选择有价值的回归用例，具体字段、枚举和阶段定义以技术设计为准，不在本文复制第二套 Schema。

| 关注点 | 应验证的行为 |
| --- | --- |
| 请求校验 | 未知字段、非法枚举、预算上下限、数字字符串／布尔值误作整数、过滤空数组返回稳定字段错误 |
| 条件缺失 | 购机预算／用途缺失；维修检查省略为未知，`checks_done=[]` 为尚未检查；数组显式 null 在格式校验中拒绝，预算／系统的合法 null 才按未知处理；字段路径与场景一致 |
| 配置分层 | 只改 RRF／重排／预处理时索引 hash 不变、查询 hash 改变；改变文档模型／分块时索引 hash 改变；不兼容编码器被拒绝 |
| 配置标识 | 键顺序不影响规范化 hash，语义配置变化影响对应身份；不把部署地址或凭据算入内容 hash |
| 可见性决策 | public／internal 与调用身份组合正确；停用／撤回不因降级而放行。数据库层实际过滤另测 |
| 生命周期 | 已验证配置下正常任务自动放行；未放行／失败候选不发布，新配置与异常转人工；拒绝不能被重试绕过；事务、幂等发布与中断恢复另用集成测试 |
| 检索编排 | RRF 使用 rank；必要上下文不能被预算截断；模型失败回退后仍保留原有条件与告警 |
| 状态和阶段 | 技术降级与无证据分开；迭代一至三不可提交反馈，迭代四仅在查询记录保存成功后声明反馈可用；写入失败仍返回已校验结果与 false，无有效记录拒绝反馈 |

配置身份的单测不能替代“查询调参不增加数据库构建记录、索引升级在维护窗口完成且失败不部分切换”的集成测试；权限决策的单测不能替代 API 和 SQL 路径上的真实权限检查。

## 8. 运行与合并约定

以下为实现后应支持的命令，当前不能据此宣称已有测试可运行：

```sh
python3 -m pytest tests/unit tests/contract
python3 -m pytest tests/integration
```

第二条需要隔离的 PostgreSQL 和对应阶段扩展；CI 应明确初始化、迁移和清理，严禁复用生产库。端到端验收使用该阶段的启动与验收入口，真实模型评估独立运行。

- 开发时先运行与修改直接相关的用例；修复失败并通过后，无新变化无需反复重跑相同检查。
- 每次合并至少运行全量单元和离线契约测试；改变 ORM／事务／过滤／配置切换／持久化行为时，同时运行相应真实 PostgreSQL 集成测试。
- 发布迭代时执行空库启动、上一版本升级、实际 API 与 Worker 验收；模型阶段运行真实检索质量评估。
- 首期不设置任意的全项目 100% 覆盖率指标。用行／分支覆盖报告发现重要业务分支遗漏，不以大量低价值断言换取百分比。
- 汇报实际执行命令、通过／失败／跳过范围、外部依赖是否使用 fake，以及尚未验证的层次。格式检查、单元测试、模型效果评估不得互相替代。

## 9. 测试评审要点

评审者应能从用例看出：保护了哪个契约；如果实现违反该契约是否会失败；失败是否可复现；mock 是否只位于必要边界；是否还需要数据库或真实模型验证。若用例只是验证 mock 返回自己配置的值、只检查代码结构或重复实现逻辑，应改写或删除。

本规范是整个项目的测试约定。新增模块复用相同原则；具体需求和字段变化更新技术设计与对应测试，避免持续扩张无关的通用检查清单。

## 10. 功能开发完成定义（Definition of Done）

新增功能、功能修改和缺陷修复，满足以下条件才算开发完成：

1. **功能可用**：满足约定的验收条件，已接入实际 API、后台或命令入口。
2. **原有功能正常**：未约定修改的接口和行为保持兼容，受影响的旧功能回归通过。
3. **基础测试通过**：补齐新行为及主要失败分支的测试，全量单元、离线契约测试和已有 CI 必需检查通过。
4. **按影响补充验证**：涉及 API／数据库时运行相关集成测试；涉及检索／模型时用固定数据比较效果；涉及性能或数据迁移时完成相应验证。不要求运行无关检查。
5. **交付完整**：必要的文档、配置和迁移同步更新，简要记录测试命令、结果及已知限制，无阻塞问题。

必需检查未运行或未通过时，标记为“验证未完成”，不能通过跳过测试宣称完成。检查后修改了实现，应补跑受影响的检查。

开发完成不代表已发布；阶段发布另按[技术设计第 8 节](/home/kurfuerst/Coding/nju/itxiaRAG/docs/phase1/phase1-technical-design.md)验收独立运行与升级。
